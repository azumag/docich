## 0. 何を作るか

配信の番組ローテーションに、**落ち物パズル（ぷよぷよ型）のクローン**を追加する。

- ルールは広く知られている落ち方ペアの標準ルール（6列×12段 + 1段隠し、4色、4個消し、連鎖倍率、
  おじゃまぷよ送受信）に沿い、**実装はスクラッチのオリジナルコード**とする。
  商用ゲームの素材・逆コンパイル物・コードは一切含めない。数値テーブルは簡略化した近似である旨を
  モジュール先頭と本書に明記する。
- PR-1（本PR）は **Twitch・ゲーム・VM への I/O を一切持たないオフライン中核**のみ。
  状態はすべて JSON 直列化可能で、将来の corner tick からそのまま永続化できる。
- 自己対戦用の決定論的グリーディ AI を同梱し、テストと将来の改善ループの土台にする。

## 1. ゲームルール仕様（PR-1 実装スコープ）

`src/docich/puyo_corner.py` に実装。すべて決定論的（seed 指定で再現可能）。

### 1.1 盤面とペア

- 盤面: 6列 × 12段（可視）+ 1段（隠し出現行、row 0）。合計 13×6。
- 色: 4色固定（`R`/`G`/`B`/`Y`）+ おじゃまぷよ `O` + 空き `.`。
- ペア: 軸ぷよ + 子ぷよ。出現は **縦（子が上、子は隠し行・軸は最上段可視行の col 2）**。
- ペア生成: 4×4=16通りの順序ペアから一様選択。乱数は JSON 直列化可能な小さな LCG で、
  状態に `rng`（整数1個）として保存される（seed で完全再現）。
- 先読み: 次の1ペアを `next_pair` で保持（将来のビュー表示用）。

### 1.2 操作と回転（簡略化した「通」式のキック）

- 操作: `left` / `right` / `cw` / `ccw` / `soft_drop`（1段落下、着地でロック）/ `hard_drop`（即着地）。
- 回転のキックは次の優先順位（通の代表的挙動のサブセット）:
  1. 通常回転（子の移動先が盤内かつ空き）
  2. 壁での軸ずらし（子が左右の壁の外に出る場合、ペア全体を壁の逆側へ1列ずらす）
  3. 床起こし（子が床の下に出る場合、ペア全体を1段上げる）
  4. いずれも不可なら回転は何も起きない（no-op）
- 空きマス以外への回転（回転入れ・Sずらし・双回転の連続利用など）は対象外。将来拡張として明記。

### 1.3 連鎖と得点（通式の簡略版）

- ロック後、同色4個以上の連結グループを検索して消去 → 重力 → 再検索を繰り返す（= 連鎖）。
- スコア式（1ステップごと）:
  `(連鎖倍率 + 色数ボーナス + 連結ボーナス合計) × 10 × 消した色ぷよ数`
  - 連鎖倍率: 1連鎖=0, 2=8, 3=16, 4=32, 5=64, 6=96, … 19連鎖以降は512で頭打ち
  - 色数ボーナス: 1色=0, 2色=3, 3色=6, 4色=12
  - 連結ボーナス: 4個=0, 5個=2, 6個=3, … 10個=7, 11個以上=10
  - **1連鎖のみの消去は0点**（原作と同じ。おじゃまも送れない）
- おじゃまぷよは色ぷよに隣接して消える（おじゃま→おじゃまの連鎖はしない）。得点には入らない。
- 全消し: 盤面が完全に空になったら `all_clear_pending` を立て、**次に消去が起きたとき**に
  連鎖倍率へ +2100 を一度だけ加算する。
- 消去上限: 1ロックあたり24連鎖で fail-closed（超過は `PuyoCornerError`）。スコア上限 999,999,999。

### 1.4 おじゃまぷよの送受信

- 攻撃量: `(持ち越し + 当該ロックの得点) // 70`、余りは次へ持ち越し。
- 予備（受信待ち）上限 30個、超過分は切り捨て。1ロックで落下するのは最大30個（6列×5段）。
- 落下順: 底の段から平らに、左から右（決定論的）。色ぷよの上に積まる。
- タイミング: 自分の連鎖解決の**後**に予備が落下する（落下直後の連鎖では消えない。原作と同じ）。
- マッチ（2席）: 各席の `attack_pending` を毎tick相手の予備へ移送。

### 1.5 試合（マッチ）管理

- 2席（`A`/`B`）で別seedのゲームを並行実行。片方がゲームオーバーで `winner` 確定、
  同時なら `draw`。
- **時間制限**: 15,000 gravity tick で打ち切り。その時点でスコアが高い側の勝ち（同点は draw）。
  無人の対戦が永久に終わらないことを構造的に防ぐ（AGENTS.md の「試合は完走させる」原則）。
- アクション数・tick 数にも安全上限があり、超過で `FAILED`（fail-closed）。

### 1.6 決定論的自己対戦 AI（グリーディ）

- `greedy_policy(state)`: 現在のペアから到達可能な全 (回転, 横位置) の着地を盤面クローン上で
  シミュレート（回転→平行移動→hard drop→連鎖解決）し、
  `得点×100 − 最大高さ×4 − 凹凸×2 − 合計高さ` が最大の置き方の**最初の1手**を返す。
  同点は探索順の最初を採用し、完全に決定論的。
- `run_greedy_match(match)`: 両席をグリーディで完走させるドライバ。seed 20260918 の実測:
  32 tick・B勝ち・A 320点/3連鎖 vs B 1060点/10連鎖・所要0.34秒。
- この AI はプレースホルダであり、将来の corner tick・改善ループ（観測→戦略更新→検証）は後続 PR。

## 2. 既存基盤との関係

- **状態永続**: `trpg_corner.py` と同じ atomic write（mkstemp + `os.replace` + fsync）と
  flock 共有ロック（`with_lock`）を利用。壊れたファイルは fresh state へフォールバック（fail-closed）。
- **コーナーローテーション**: 未接続。将来は `puyo` adapter（合成ビュー）として
  `corner_catalog.py` に **既定無効・手動予約可** で追加を提案する（本PRでは行わない）。
- **参加型対戦（#699）**: マッチ構造（2席 + おじゃま送受信）は「同志と対戦できるぷよぷよ」の
  土台をそのまま再利用できる。視聴者入力の割当（どの席を視聴者にするか）は後続設計。
- **共通配信基盤**: 触らない。エンコーダ・音声・通知・ステータス枠は変更しない。

## 6. 安全性

- **著作権**: ルール・数値テーブルの簡略化された再実装のみ。素材・コードの持ち込みなし。
  モジュール docstring にも明記済み。
- **fail-closed**: 連鎖上限・アクション上限・tick上限・おじゃま上限・状態サイズ上限
  （256 KiB）・入力検証（不明なアクション・壊れた状態は拒否）。
- **完走保証**: マッチは時間制限で必ず終わる。暗黙の強制終了はしない（tick打ち切りは
  スコア比較による明示的決着として記録）。
- **機密情報**: 状態ファイルにトークン・個人情報は含まない（盤面と数値のみ）。
