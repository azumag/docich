# 半熟英雄のscript bot

`config/games/hanjuku-hero.toml` は `brains/hanjuku/bot.py` を1.5秒間隔で起動する。
Python標準ライブラリだけで画像を判定し、決定的なルールでSNESのpad入力を返す。
戦闘中に軍色を持つ歩行断片が残り、6体の完全な兵士を読めていない側は、少人数や0人へ確定しない。未読として再観測し、白兵優位・卵温存の兵数根拠に使わない（v197）。

実メニューで単独の短い上下移動を計画した直後は500msで再観測する。到着の実画面を読んでから確定し、A/Bや未読/暗転はこの高速化の対象にしない（v196）。
Claude、OpenCode、API、認証情報を操作時に使用しない。旧`brain.py`は互換テスト用に残すが、
この設定からは実行されない。OpenCodeによる試合結果からの自動改善は後続作業（Issue #954）とし、
今回のbot操作はそれに依存しない。bot版は `hanjuku-chart-v2`。

コードはOS層・戦略層・判断層・手順層に分かれている（`src/docich/hanjuku/`）。
本書で `hanjuku_policy.py` / `hanjuku_bot.py` の関数として記載している処理は、
互換ファサード経由で同じ名前のまま参照できる。各処理の置き場所と、改善時にどの層を触るかは
[層構造](hanjuku_layered_architecture.md) を参照。

## 実表示名による敵の技メニュー判定（v204）

実画面の「フリージボーイ」を、技表の「フリージーボーイ」と所有者判定時だけ照合する。g747原8867/8868では青い敵HP144と技「エアコン」「れいとう」を読めていたが、名前の表記差で所有者不明となり上下入力を送っていた。保存した原PNGの方策再現では敵側と判定して待機する。名前が不明・似ているだけの場合や、両軍の技に一致する曖昧な場合は所有者を確定しない。技表の正規名と他の戦術は変更しない。

敵メニューの待機回数は、同じメニューをJSON保存・復元しても保持する。新しいメニューでは回数を初期化し、既存の30観測上限とその後の有限な操作を維持する。原画像の再現テストは自然な新戦闘・技発動・勝敗の証明ではない。

## 現在の名簿と月初の補充予算（v203）

同run・章・月の完全な将軍一覧と本人ステータスを読み終えた場合、卵回復の対象と予約費用を現在の在籍者へ絞る。過去の残数0・要再確認・数量履歴は消さず、名簿が未確認・別月・別run・走査中、または雇用到着待ちなら従来の予約を維持する。未知の卵を回復済みにはしない。

g747の2年4月は実兵0、70G、完全名簿の賃金6Gに対し、一覧にいない将軍の卵予約40Gが残っていた。卵優先で補充計画が0になり、終了確認では再び24人へ戻るため、補充画面に到達しなかった。元PNGと保存状態のローカル再現では、修正後は予約を照合して通常50人の補充を選ぶ。実購入・支払い・新人数は別途実画面で確認する。#2115の終了拒否上限は維持する。

補充の再計算と数量確定は同じ実残金・完全賃金・卵回復・修復・未購入札・雇用予約を使う。未知賃金は30G、既知の高額賃金は全額残す。実在籍者の追加で旧名簿を無効にする際も、確認済み賃金と追加本人の固定賃金を支払いの下限として保持し、新しい完全名簿の実賃金で置き換える。これは在籍総数や収入の証明には使わない。支払い待ち・支払済みの数量画面でAを再送しない。

## 画面の構造化（`hanjuku_font.py` / `hanjuku_screen.py`）

- 半熟英雄の描画は `video_scale=1.0` と `video_force_aspect=true` を組み合わせる。
  Snes9xでは約299×224になり、従来の897×672と同じ縦横比を保って描画・キャプチャ量を減らす。
  小さい描画の使用は2026-09-27のオーナー指示に基づく。他のRetroArchゲームの描画サイズは変更しない。
  配信側だけがnearest-neighbourのcontainで960×540枠へ拡大・中央配置し、余白を黒で埋める。
  `video_force_aspect=false` として窓だけを256×224に合わせない。実ゲーム内容が縦に縮み、
  名前画面や字形の判定が壊れる。画像認識は配信後の映像ではなく、ゲーム窓全体を取得して
  256×224へ正規化する既存経路を使用する。設定の反映は次のゲーム起動時。
- 文字はSNESの8×8タイル格子に描かれる。名前入力表から採取した字形137種（ひらがな・カタカナ・
  数字・英字・記号）と濁点/半濁点（上段タイル）の2値ビットマップ（`hanjuku_glyphs.py`）と
  完全一致したタイルだけを文字として読む。一致しないタイルは不明として扱い、推測しない。
  画像そのもの・ROM・セーブはリポジトリに含めない。
- 読めるもの: 月初ヘッダー（年・月・所持金・メインメニューでは話数）、メニュー項目と手カーソルの
  選択位置、会話文（「〜しょうぐんが 〜じょうに のりこんだ!!」「〜じょうが てきに せめこまれました」
  「きょうさく」等）、商人の品目と価格、個数入力、戦闘パネルの将軍名とHP、出撃確認の携行切り札。
- マップ: 通常カーソル（白い角括弧）と出撃先マーカー（青いG）、城の屋根（敵=青、自軍=赤）。
  本番スクリーンショット（897×672）でも同じ読みになることを、過去に本番で取得した画像で確認済み。

## あたしの家での卵修理（v83）

- 対象は主人公を含む全将軍。第1・2章の月ごとに、通常の出撃操作の切れ目で X → しょうぐん → ステータスを巡回する。城内・フィールドを区別し、「たまごこわれている」を読んだ本人だけを修理に向かわせる。使用回数0や「なし」を卵割れと取り違えない。全体マップで家の位置を未実測の第3章以降は派遣しない。
- 城内では城名・本人の在城・他に残る将軍を実表示で確認してから出撃する。代役への差し替えをせず、城の最後の1人は修理に出さない。フィールドでは将軍一覧の本人を選んでSELECTで位置へ移り、部隊のステータスで本人を再確認してから「いどう」を選ぶ。主人公はフィールドのSELECTでも移動できる。
- 家へ向かう Y マップの選択セルは第1章 `(118,126)`、第2章 `(128,94)`。ハートの描画中心は各々 `(118.5,126.5)`、`(128.5,94.5)`。戦闘と月替わりは既存方策で進め、メニュー操作中に割り込まれた場合は派遣の確認を取り消す。既存の緊急帰還が始まれば修理を中断する。
- 実表示の3品目・価格と所持金を読み、賃金用30Gを残せる最も高い品を選ぶ（スカーフ200G、みずぎ100G、ピアス50G）。選択入力は一度だけ。購入後に本人の卵表示と同月の正確な所持金減を照合して `house_repair_verified`、不足・読取不明・不一致は未確認として記録する。ピアスは卵を使用回数0で復活させるので、月初の既存卵回復とは別の操作になる。
- ギフト一覧は B で閉じない。到着後に資金が不足した場合は、所持金より高いスカーフを選んで、実測済みの「おかねがたりません」分岐で支払わず閉じる。
- 終了後は本人の部隊メニューの「きかん」から、Rカーソルの下に自軍の赤旗が見える城へ帰還を指示する。`house_return_requested` は指示の証拠であり、城への到着確認ではない。
- メニューの各段階24観測、移動240観測、全体1200観測を上限にする。`house_scan_*` / `house_egg_seen` / `house_dispatch_requested` / `house_purchase_requested` / `house_repair_verified` / `house_deferred` 等の判断記録を残す。新しいworker・queue・provider・モデルは追加しない。既存の世代別bot state・判断記録経路を使い、配備は次観測のホットロードで反映する。
- `tests/test_hanjuku_house.py` は実測配置を合成画面で再現し、全将軍の対象化、名前・価格の誤読、守備維持、資金不足、購入重複、支払だけでは成功にしない条件、割り込み、上限、帰還先の所有を検証する。ROM・保存状態・実フレームはGitへ含めない。

## 操作と終了条件

- 名前入力: ひらがな表を手カーソル位置で移動し「どうし」を1文字ずつA入力する。名前欄の実表示が
  「どうし」と一致した時だけSTARTで確定し、目標の前方一致でなければBで1文字削除する。未分類の字形を除去して名前一致とせず、
  未読文字が残る場合や名前画面を構造化できない場合は入力・確定を保留する。
  手が目標文字に重なって読めない場合は実測済みの表配置から目標セルを求める。
- チャート（`hanjuku_chart.py`、出典 `games/hanjuku-sfc-speedrun` の charts/1.md・overview.md。
  原典は [ブラッキーチャート冒頭](http://blog.livedoor.jp/hanjukueiyu/archives/1035528547.html)
  （同リポジトリ README が転記元と明記。アドリブ前提・連射機禁止・基本切り札
  ブラッキー/クースカン/ファバード・敵に卵を使わせない方針も原典由来）:
  第1話は 1-A1 どうし→キカンドン、1-V1 ヴィーナス→ナキューメラ、1-C1 ココット→ジョンリギ（チャート表記
  ジョリンギ）を切り札なしで出撃し、占領を確認した城から 1-A2 フットバース→ゴーメン、
  1-V2 フットバース→カストーラ、1-C2 ダイチスイム×2・ブラッキー→スペンソニア、1-A3 どうし→スペンソニア、
  全城占領後に 1-B1 クースカン・ノリウツールを持ってボス（結界の塔）へ向かう。
  戦術は ガルバンゾー戦で主人公は敵HP24以下でフットバース、ヴィーナスは開幕フットバース、
  ココットは白兵後に敵HP13以下でダイチスイム、タピオカ戦は開幕ダイチスイム・ブラッキー、
  クイーン戦は最初のぶつかり合いの後にクースカン→ノリウツール。それ以外は白兵でAを押して踏ん張る。
  チャートに戦術のない場面（敵の卵召喚、切り札未指示の戦闘メニュー）は、チャートに沿った上で
  状況から独自判断する（`egg_battle` / `independent_menu`）。判断と勝敗は `run/hanjuku_experience.json` に
  状況キー単位で保存し、次回は勝率の高い方を選ぶ（`hanjuku_experience.py`）。チャートが指示する
  戦術は常に優先する。実測は未実施のため、勝率改善は未確認とする。
- 戦闘中の切り札は出撃で携行した札だけを計画する。選択した札の実使用告知が未校正のまま戦闘が終わると、
  その札は当該出撃の携行から外し（`kit_spent`、同じ手順の再出撃でリセット）、次の戦闘で使い切った札を
  再計画しない。読み取れる札名が無い一覧でも、開いた一覧（`card_flow.stage=list` の text 画面）は
  `battle_card_missing` として B で閉じ、A連打で停止しない（g452 07:14 ヴィーナス）。

### 保留の廃止（入力0件の有限ゲート、v128）

- owner方針（2026-10-03）: 「保留」は終状態にしない。保留したままでは画面が止まり、何も進まない。
  フェード中やメニュー描画中の**有限回の待機は残す**が、上限を超えた後は必ず入力を出す。
- 判定は `hanjuku_bot.decide()` 末尾の連続入力0件ストリーク。数えるのは
  「policyが入力を出さなかった」かつ「フレームdigestが直近2種のいずれか」という観測だけで、
  `NO_INPUT_HOLD_MAX = 100` を超えた時にフェーズ別の既定入力を送出する（`no_input_fallback`）。
  digestが直近2種から外れた（フェード・アニメ・部隊の移動）観測は数え直し、policyが入力を
  出した観測も0に戻す。2種の画像を「1つの未変化画面」とみなすのは `hanjuku_run.screen_stalled` と
  同じ扱いで、カーソルが明滅するメニュー（g358）でゲートが発火しないのを防ぐ。
- 上限の根拠: 既存の有限待機（`RECALL_LIMIT=90`、`EGG_RITUAL_LIMIT=64`、`RARE_SCAN_LIMIT=32`、
  `RECRUIT_CANDIDATE_LIMIT=32`、`MONSTER_MENU_HOLD_LIMIT=30`、`house.STEP_LIMIT=24`）はすべて
  これを下回るため切断しない。通常1500ms間隔で100観測＝150秒であり、
  ランを終了させる `hanjuku_run.STALL_SECONDS=300` より先に手を出す。
- 入力の選び方: `summer_bonus` は未確認の解雇を防ぐため上を1回押して再観測する（v130）。
  その他は既存の `legacy_actions`（フェーズ既定: 確認画面＝A、店＝B、タイトル＝START 等）を
  適用する。それが空になる5フェーズだけ、次の鍵を使う。
  - `field` かつ `unknown` / `map`: `select`。主人公の位置へカーソルを再中央化し（実測済みの挙動、
    `map_step.select_focus` と同じ `nav_last` / `uncertain` の扱い）、画面を動かして nav を再アンカーさせる。
    素のマップでAを押すと未知のセルで出撃メニューが開くため使わない。
  - `field` かつ `map_target` / `world_map`: `b`（マップ表示の取消・退出）。
  - `field` その他（フィールド上のテキスト表示など）: `a`（メッセージの確認）。
  - `transition`: `a`。止まった暗転だけが対象で、フェードは描き変わるためこのゲートには来ない。
  - `name`: `b`。削除だけを行い、未読の名前画面で入力・確定はしない（`name_confirm` を盲打しない既存方針を維持）。
  - `field_menu` / `battle`: `b`。読めないメニュー・戦闘パネルは閉じる／取消／退く方向へ戻す。
    `_hold_deploy`（出撃確認・将軍一覧・城メニュー等の長期保留）はこの `b` で解除される。
- 記録は `no_input_fallback`（`phase` / `screen` / `observed_metric.frozen_observations` /
  `frame_sha256`）。`SPOKEN` には入れない（待機と同様、記録するだけで実況しない）。
  `INPUT_CONTEXT_DECISIONS` にも入れない（保留の説明を担った既存記録を、この機械的な追従入力で
  上書きしない。`strategy_variant` / `deviation_reason` を既定値で潰さないため）。
  `hanjuku_decisions.jsonl` の `action_plan.reason_decisions` と各行 `decision` に出る。
- 検証は合成Canvasのみの `tests/test_hanjuku_no_input_gate.py`。100観測までは空を維持し、
  101観測目でフェーズ別の鍵が出ること、描き変わる画面では発火しないこと、
  既存の有限待機（敵モンスターメニュー30観測）を先取りしないことを確認する。
  実機の `hanjuku_decisions.jsonl` での発火は未観測。

### 低HP時の救済

- 読み取れた双方のHPが正で、味方HPが開始時の40%以下かつ敵より少ない、または味方HPが12以下なら、Bで戦闘メニューを開く。剣術の稽古（どうし・だいじん、開始90対90、出撃なし）は対象外。当該時点で実行条件を満たすチャート戦術は先に処理する。
- 実際に読める切り札リストから、エンジェリンによる回復、ダメージ下限で倒せる札、通常将軍の卵落下に適合する札を評価する。卵落は gcgx の規則「卵落 > 敵・味方将軍の最大HP合計 mod 16」で判定する。最大HPは負傷した戦闘中HPではなく固定値（`hanjuku_egg_reference.GENERAL_HP`、主人公は持ち越しの全快HP `ref_ally_hp`）を使う。未知将軍やボス将軍に卵落下を保証せず、召喚リスクがある相手には固定順位だけで非致死の札を選ばない（下記v132の判定）。自軍にも被害のあるデッドガン・ファバードは自動救済の候補にしない（効果と卵落の参考: [攻略・解析の切り札表](https://gcgx.games/hanjuku/kirihuda.html)）。卵落の表は `hanjuku_reference.EGG_DROP_VALUES` に保持する（gcgxとwikiwikiの切り札表が一致する全32札の `CARDS` から導出）。
- 安全な未試行の札がない・札が使用不能なら、読める「たまごをつかう」へ進む。防衛戦で卵だけが有効なメニューも認識する。戦闘用の騎士カーソルを追い、無効な先頭行にカーソルがあれば目的行まで動かしてからAを押す。
- メニューの応答待ちは最大3回（戦闘全体で12回まで）、切り札一覧確認は最大3回、同名札と卵の選択は各1回。メニュー／一覧の認識待ちと移動にも上限を設ける。読めないカーソルでAを押さず、救済手段が尽きたら白兵に戻る。無条件の勝利や撤退は保証しない。
- `battle_survival` / `battle_survival_select` にHPと選択理由を記録し、対象フレームを保存する。札を選択しただけでは消費を確定せず、既存の `cards_selected` / `cards_unclassified` と実使用証拠を区別する。救済は経験記憶の `pass` では抑止しない。
- botは各観測で別コマンドとして起動されるため、方策・画像認識の配備は次の観測から読み込まれる。実行中のゲームを再起動する必要はない。配備後は `bot_version=hanjuku-chart-v135-month-foreground-state` と新しい判断記録で反映を確認する。

### 切り札の撃破判定（v132）

- 通常将軍戦では「札の基礎威力＋自軍の現兵士数による加算」から、敵兵士の残HP上限を差し引き、敵将軍の現在HPを落とし切れるか計算する。例えばゼンマインは将軍戦32だが、敵兵士6人が各HP10なら兵士分だけで60あるため、将軍へのダメージ下限は0。将軍のHPだけを32と比較しない（[実走者のダメージ式と例](https://karzu.exblog.jp/24199919/)、[指定RTAチャート](https://blog.livedoor.jp/hanjukueiyu/archives/1035528547.html)）。
- 将軍型ボスはボス用威力で、自軍兵士による加算はしない。プリンス・せいめいたいの兵士は最大HP100で計算する。[第3話の兵士HP100](https://gcgx.games/hanjuku/03.html)と[第9話の兵士HP100](https://gcgx.games/hanjuku/09.html)を一般兵HP10と混同しない。クースカンを2回選択したという記録だけで、兵士HPを25へ減らさない。
- 今の画面で兵数が読めなければ、自軍0・敵軍6を保守的な境界にする。古いフレームや別戦闘の兵数を現在値へ流用しない。未知の敵・HP・効果から撃破保証を作らない。`lethal=false`は「この下限では撃破を保証できない」であり、「必ず生き残る」という実測結果ではない。
- 卵持ちの敵には、必要な回復、単発撃破、通常将軍への卵落下目的、実一覧の後続札を確認した制御・半減の連携の順に評価する。非致死の攻撃札にこれらの根拠がなければ、確認できる卵等の救済を探す。札が実際に使える防衛メニューで奥の手を押せるとは仮定しない。連携でも一枚ごとに実HPと兵数を再観測する。
- 撃破を保証できないことだけを理由に、健康な将軍をすぐ退却させない。戦闘通算の既存回数・HP損耗予算内で1 tapずつ白兵を観測し、HP・兵数の読取値が変わったときだけ保留した札を再評価する。兵数の既知・未読の往復で一覧を開き続けないよう、実一覧の再照会も同じ通算予算へ計上する。拒否ごとに予算を戻さず、危険時や上限後は実メニューの退却・防衛の既存処理へ進む。予算境界の新観測で、直前の実一覧にあった札が単発撃破または必要回復になった場合は、戦闘通算で一度だけ実一覧を再確認する。追加の白兵予算は与えない。
- 通常戦術・救済札とも、最後のAを押す前に再評価する。ホットロード前の `card_flow` もこの判定を通す。拒否した札を欠品・使用済み・卵落下済みにせず、同じ状態での一覧開閉の反復を抑える。
- 現在の完全な白兵パネルは旧版の召喚フラグより優先する。既召喚の例外には現在版が実際に見た召喚メニューを必要とし、別の将軍・不整合なHPを観測した後は旧敵の卵情報や旧HPでAを確定しない。
- `battle_card_damage_rejected` / `battle_card_damage_replan` / `battle_card_damage_recheck` と既存の札判断記録に、現在HP・兵数・対象種別・総威力下限・将軍へ届く下限・卵落適合・選択理由を残す。予測、選択予定、実使用、卵落下、撃破の証拠は引き続き区別する。
- 同じ固定文実況を繰り返さないよう、既存の `[hanjuku.narration].enabled` をfalseにする（owner 2026-10-04）。監視側は毎回設定を読み直すため、正規配備後に新しい固定文の投入を止める。終了ランの未配送候補を再送する入口でも設定を再確認し、無効・未読なら無音で次の音声へ進める。すでに再生中の音声は途中で切断しない。状況に応じた生成実況の配線は別の変更で行い、この無効化だけで生成実況が動いたとは扱わない。

### 卵回復の見積もりと賃金フロア（v133）

- 月頭の2つの金額を分ける。**予約（`shop['reserve']`）は上側バウンド**で、出撃画面を読んでいない再チェック対象（卵召喚を試した将軍）も1個50Gとして数える。これは兵士へ渡さない金であり、実額（`NこでNG`）の支払い後に0へ戻して兵士へ解放される。読み取り前の金額を兵士へ使わせないための枠で、失われない。
- **画面を開く判定（`shop['egg_cost']` / `_egg_estimate`）は下側バウンド**＝実測で残数が減った卵だけを数える。再チェック名は「確認対象であって債務ではない」ため、それだけなら0G。g574 2-9 では読み取り前の1名を50Gと見積もって所持金55Gのまま画面を開けず、3-2 では2名を100Gと見積もったが実額は50Gだった。`month_extras_plan` の `egg_recover_estimate` に見積もりを残す。
- 兵士より先に卵へ回す月（`egg_priority`）は「**1個分の回復費＋賃金リザーブ**」で開く。実額は画面だけが知るため、見積が高くても1個分払えるなら開く（g498: 見積150G・実額50G）。再チェックだけの月は0Gから、賃金リザーブ30Gが残れば開く。
- 支払い（`うむッ!`）は**実額＋賃金リザーブ30G**（＋家修復予約）を満たす時だけ確定する。これ以前の判定は見積もり＝下側バウンドなので、支払時が最後の防衛線になる（owner 2026-09-28: 賃金リザーブは守る）。100Gで100Gの回復は確定しない。
- 築城など**任意の支出だけ最悪ケース**で抑える（`_chikujou_reserve` は全対象×50G）。読めていない卵の可能性を、任意支出に後回しにしてよい。

### 原典の将軍vs将軍・戦術6パターンと独自判断の対応

原典冒頭の6戦術（①〜⑥）は、チャート指示がある場面では `CHAPTER_1_TACTICS`（card_flow）が常に優先する。
チャートが当該フレームに切り札を指示しないとき、通常の `independent_menu` / `egg_battle` は、
観測可能な範囲で次の既定に写像する（`hanjuku_policy.battle_menu_step` / `egg_battle_step`）。

| 原典 | 内容 | 独自判断への写像 |
|---|---|---|
| ① パワー全開で押し込む | せんとう勝ち・卵なしなら白兵押し切り | HP不利なし → `pass`（白兵継続） |
| ② 切り札で兵士削り→押し込む | チャート指示の切り札（card_flow） | 通常はチャート指定。低HP時は後述の救済選択 |
| ③ パワー調整・中央ぶつかり/壁当て | せんとう同格の白兵調整 | HP同格/有利 → `pass`（①と同じく白兵継続） |
| ④ クースカン後は兵士消耗まで抑える→ブラッキー | チャート指示の切り札 | 通常はチャート指定。救済時の選択は後述 |
| ⑤ ファバードで勝つ | チャート指示の切り札 | 通常はチャート指定。救済時の選択は後述 |
| ⑥ 自軍が卵を使って勝つ | 白兵+切り札で足りないとき、卵なし敵へエグモン | HP不利かつチャートに切り札指示なし → `use_egg`。勝てそうなら `attack`（卵温存） |

- 敵の召喚（`egg_battle`）は原典「敵に卵を使わせない」方針が既に破られた局面のため、
  通常は `use_egg` で応戦する（経験記憶で `attack` に切り替え可能）。これは⑥の「自軍が卵を使う」
  に相当する。「たまごつかわなくても勝てそうな相手」では卵を温存する（`egg_action=attack`）。
  温存は次の条件がすべて成り立つ時だけで、片でも欠ければ従来どおり卵を使う（fail-closed）。

  - 強い将軍ではない（`_strong_enemy`、shogun.html の評・ボス）。
  - 白兵の合戦力が敵の7割を超える。合戦力 = HP + 10×兵士（gcgx battle.html「兵士は1人ずつHP10を持っている」）。
    兵士は戦闘フィールドのスプライトを数える（味方が左・敵が右、`hanjuku_screen._field_soldiers`）。
    片側でも重なりを見つけたらその側は `None` となり、判定はHP比較へ退ける。
  - 自軍のHPが最大の7割を超える。30/82 のように大破していれば敵将軍の絶対値HPが低くても温存しない。

  判断は `mem['egg_needed']` に保持し、劣勢になったら一方向に `use_egg` へ途中昇格する
  （回復しても `attack` へは戻さない）。温存中はまず白兵で戦い、g460 の退却ゲート
  （卵も札も無い局面だけ先に退却を試す）は開かない。低HPの救済は次の追加ルールで扱う。
- 原典は「白兵で勝てそうなら白兵、不足なら切り札、それでも足りなければ卵」と優先順位を明記する。
  通常の独自既定はこの優先順位に従う。瀕死ではHP差だけで勝てると決めつけず、以下の救済を優先する。
- 具体的な切り札名・タイミング（ファバード多投、クースカン→ブラッキー等）は原典チャートの
  各話手順（`games/hanjuku-sfc-speedrun/charts/*.md`）が正本。2話以降の指示も同チャートから
  エンコードするが、各章の`CASTLES`座標が計測済みでなければ`orders()`が空を返し
  `chart_unavailable`として扱う（推測座標で後半チャートを実行しない）。
- 敵が卵持ちで激突位置トリガーを持つ場合も、チャートが白兵の進行を前提にした札を指示している戦闘
  （`after_clash` の 1-B1 クイーン、`when_hp_at_most` の 1-A2 ガルバンゾー等）では押し込む
  （`_charted_melee`）。入力を保留するとぶつかり合いやHP条件に到達せず、札が発火しないまま
  敗北する（g454 08:19 クイーン、g456 14:13 ガルバンゾー）。チャート指示のない戦闘では
  従来どおり激突リスクで保留するが、同じ戦闘で8回保留したら以降は押し込む（`MELEE_HOLD_LIMIT`、
  無期限の保留で死ぬのを防ぐ）。
- 卵持ち敵のHP条件札がその戦闘で最初の札なら、条件HPを待たず開幕に前倒しする
  （`egg_denial_timing`、オーナー指示 2026-09-29「卵を使われる前に切り札で倒すべき」）。ぶつかり合いが
  先に敵の卵を誘発するため、HP13以下待ちでは遅い（g460 16:08: ココットの 1-C2 ダイチスイムが
  ぶつかり合いの後に発動し、ガルバンゾーがカメレオンマンを召喚）。クースカン開幕→ゼンマインHP25のような
  連鎖の後続札は従来どおりゲートを守る。
- 将軍（最大HP）と切り札（卵落・将軍戦ダメージ・ID）の内部データを組み合わせ、戦闘開始時に
  卵ディニアル方針を決めて `battle_egg_plan` に残す（`_egg_plan`。`threat` が真の敵のみ記録）。
  携行札から `卵落 > (敵味方将軍の最大HP合計) mod 16` で落ちる札を選び、ID合計が47以下なら
  開幕卵も抑止する。**チャートがその札を指す戦闘では発火せず**（HPゲート・after_clash を壊さない）、
  チャートに持たない卵落札だけを開幕に使い（`eggdrop:{step}:{card}`、同値は将軍ダメージが小さい札），
  選択後の敵HP低下は `battle_egg_drop_unconfirmed` / `enemy_egg_drop_expected` として記録する。
  白兵ダメージと区別できないため、卵落・召喚不能は確定しない（v129）。出撃時の追加携行は敵の最大HPが未判明のため変更しない。
- 旧版の `enemy_egg_dropped=True` は戦闘観測で一度だけ無効化する。選択予定だけで卵リスクや救済確認を省略しない。
  白兵のチャート指示、8回の保留上限、HP損耗予算、A 3 frames + release 50 msを4回の入力は維持する。
  卵落下の直接的な画面署名と青バー自体の画素検出は未校正。出撃時のdropper携行拡張も未実装。
- 通常の切り札も、救済と同じく実カーソルから1入力ずつ移動し、対象行を確認してからAを送る（v129）。
  カーソルを確認できない・方向入力しても位置が変わらない場合は10観測で打ち切り、11回目にBで一覧を閉じる。
  11回目の現画面で有効札と本人のカーソルが一致した場合だけ、通常・救済とも従来のダメージゲートを再評価してAを許す（v136）。移動や再確認の予算は延長しない。
  選択後の告知待ちも通常/救済共通で6観測までとし、7回目に未確認としてBで戻る。
  選択前の退出では札を消費扱いせず、既存の開く操作の再試行上限を守る。旧版の告知待ち状態にも次の観測から適用する。
- 札の連鎖（`after_card`）は実使用告知が未校正のため、確認済み使用（`cards_used`）に加えて
  選択記録（`cards_selected`/`cards_unclassified`）でも継続する（`after_card_unconfirmed` として逸脱記録）。
  告知が未校正のままではチャートの2枚目（1-B1 ノリウツール）が永久に発火しないため。
- 白兵ではAを50ms押下・50ms解放する操作を4回で区切り、画面を再観測する。
  - 自軍の本人について残使用回数0を整数で観測済みなら、救済・学習判断・敵召喚への応戦・召喚候補でも卵を選ばない。数量不明を0扱いせず、選択だけで残数を減らさない（v136）。
  - 敵未召喚で実切り札行があり、自軍HPが最大の7割を超え、現在読めた双方のHP＋兵数×10で優勢なら卵を温存する。古い救済フラグや学習した卵使用意図より優先し、未読兵数では優勢を断定しない。

    自軍城への移動出撃（`move_N`）はゲーム内での受理を実機未確認。受理されなければ出撃先選択画面は
    既存の `unexpected_target` でBにより取り消される。
  - L2 採用: 同じ `request_id` への回答だけを次のマップ観測時に `chart_adjust_applied` として独立したorder列で
    採用する（`strategy_variant=chart_adjusted`）。採用済み計画（`chart_plan`）は要求状態（`chart_adjust`）と分離し、
    占領待ちなどで新しい要求を出しても保持する。置き換えるのは次世代の検証済み計画を採用した時だけ。
    計画が占領待ちの間は暫定JEVを使わない。各orderは `A:<request_id先頭8桁>:<ローカルstep>` の実行IDで
    記録するため、別世代が `J1` を再利用しても実行状態・再攻撃・実績が混ざらない。ローカルstepは
    英数字・_・- の12文字以内、基準と同名は不可。基準チャートは実行時に変更しない。
    出撃確定時にorderを実行IDごとにスナップショット（`launched_orders`）し、計画が置き換わっても
    その部隊の携行品・戦術・ボス突入照合・敗北時の再攻撃はスナップショットで続ける。突入文は
    実行IDごとの出撃記録（`sorties`: 選択した将軍・目標・確認証拠）と城＋将軍で照合し、同じ城への後続出撃が
    先行部隊の対応を消さない。候補が複数で曖昧な場合は推測せず実行IDを付けない（ボス突入は保留）。ボス出撃の判定は
    step名ではなく「目標が当章のボス城（`chart.boss_castle`）」のorderで行い、主人公・携行品の確認証拠と実測突入文の照合を
    基準ボスorderと調整orderで共通に適用する。計画を使い切った後は暫定JEV orderも実行候補に入る。
    調整・暫定orderの携行切り札は、検証済みの基準戦術（敵・タイミング）があればそれを流用し、
    無い切り札は明示の既定として任意の敵に対し開幕で1回使う（再攻撃の開幕切り札と同じ使用証拠ガード）。
    月次は調整チャートの purchases 月が来たら既存の商人・兵士補充手順で買う
    （既知価格の残額で兵士数を上限）。将軍の登用数は調整チャートの値ではなく上記のオーナー規則（月1人・条件つき）に従い、`recruit_owner_rule` として記録する。
    非同期ワーカーはworker lockを生成完了（保存・記録）まで保持し、agent/corner監視の別プロセスが同じ要求を並列生成しない。
  - L4 GO後照合: `game_over` 確定時、teardown 前に `hanjuku_chart_review.review()` が基準・保存された調整チャート・
    `hanjuku_decisions.jsonl` の実績を照合し `hanjuku_chart_review.json`（提案: `promote_adjusted_step` /
    `promote_interim_attack` / `review_base_step` / `cover_off_chart`）を書く。`hanjuku_chart.py` は編集しない。
    次回の開始案内は、直近2048ランタイムを探索し、世代・leaseとゲームオーバー証拠が一致する完了レビューから
    勝敗・実行した調整手順・成功した攻略先・見直し候補を読み上げる。履歴は案内に反映し、
    基本チャートは自動変更しない。
  要求・保存・JEV回答・ワーカー結果・照合の履歴は `hanjuku_chart_history.jsonl`。
- 2話以降のorders・tactics・purchasesはチャートからエンコード済み。ただし各章の`CASTLES`座標は
  `hanjuku_measure`で実機フレームから計測するまで空。座標が無い章は`orders()`が空を返し
  `chart_unavailable`として記録して保留（推測座標で移動しない）。計測後は本城・ボス城・
  通常城が揃った指示だけが有効になり、それ以外の章の有効な指示が無い状態は
  既存の調整チャート要求へ流れる。全ステージの実機攻略・勝率は未計測・未実行であり成功扱いしない。
  gcgxの切り札・卵落・敵卵・AIパターン・半熟レベル等の参照表は`hanjuku_reference.py`に保持する。
- 文字・カーソル・戦闘表示のどれも読めない画面は「状況判定保留」（`situation_held`）として記録し、
  従来の安全な規則（確認入力・マップでは待機）だけを使う。
- 固定20分の終了・強制セーブは行わない。名前入力とプレイを観測した後、実ROM由来のタイトル画像の
  特徴に3回以上・2秒以上一致した場合、`game_over`（根拠`title_return_after_gameplay`）とする。
  ゲームオーバー演出は確認入力で進め、タイトルへ戻った時点で入力を止める。起動時のタイトルや
  デモをゲームオーバーと扱わない。タイトルへ戻る前の敗北演出の種類までは判定しない。
- 正規化したゲーム画面のRGBが連続300秒変化しなければ`screen_stalled`とする。
  15秒超の観測欠落、一時停止、時計の巻き戻り、画面変化で計測をリセットする。
  背景アニメーションを含めて変化する画面は「無変化」ではない。
- 観測が届き続けているのに600秒・120観測以上入力を送れなければ`input_stalled`
  （根拠`no_input_sent_while_observing`）とする（#1369: 商人確認画面で約16分間
  入力保留・アニメーション継続）。一時停止・観測欠落・巻き戻しでは計測を
  仕切り直す。入力を送るたび計測は最初からになる。
- 終了候補・終了確定時は実行境界でも入力を拒否する。runtime/generation/leaseが一致する終了証拠を
  `retroarch_boundary.json`へ引き継ぎ、既存coordinatorがゲーム側の子プロセスを停止して前のゲームへ戻す。
  他のRetroArchゲームの明示pause/save契約は変更しない。
- 復帰直前にcorner監視は `hanjuku_run.terminal()` で永続化された終了証拠を runtime_id・generation・
  lease と照合し直す。一致しない・証拠が不正な場合は復帰せず失敗として止める（fail-closed）。
  起動成功receiptが返した完全なidentityをcornerのactive保存前に固定する。初回観測時に
  現在のruntimeを後から所有したことにはせず、identity欠落や同名別leaseへの置換はfail-closed。
  coordinatorにも固定した `bot_identity` を `payload.expected_source` として渡す。排他ロック内で
  完全一致を確認してから停止へ進み、観測後に別leaseへ変わった場合は `source_fence_lost` で拒否する。
  元のゲームがあればそのゲームへ、なければcoordinatorのstopでidleへ戻す。

## 音声

半熟英雄の`[retroarch] audio_enabled=true`と`audio_sink="soren_null"`で、
ゲームのBGM・効果音を既存の配信busへ出す。共通の音声busや配信エンコーダは再起動しない。
Sorenの`bgm_worker.sh`は半熟英雄中の共通BGMを止め、次のCLIゲームでは再開する。
読み上げ音声は同じbus上で維持する。
`audio_latency_ms=289`で音声バッファを確保する。本番の64ms設定で音切れがあり、
バッファ拡大と実行中エミュレータの全スレッドをnice -5へ調整した後、ユーザーが改善を確認した。
設定値は次回起動にも反映される。niceの調整は当該runtimeだけの復旧操作であり、
この設定からsudoや優先度変更は行わない。

`audio_volume_percent=80` で、presentationがゲームのプロセスツリーに属するPulseAudio
sink-inputだけを80%にする（共通sink・読み上げ・BGM worker・他ゲームのstreamは変更しない）。
ゲームがstreamを作り直しても再適用し、sink-input番号・sink名・音量・muteを
runtimeの `audio_volume.json` に記録する。

## 実況

現在、下記の固定文経路は `[hanjuku.narration].enabled=false` で配信への投入を停止している（v132）。決定記録と候補は診断用に保存する。場面に応じた生成実況は別の変更として扱う。

- botは決定記録から、画面で読んだ事実（将軍名・城名・HP・所持金・切り札・チャート手順）だけを使って
  実況文を作り `hanjuku_commentary.jsonl` へ候補として書く（`hanjuku_commentary.py`）。
  事実が読めない決定は文を作らず `held`（状況判定保留）として記録する。
- 配信へ出すのは agent/corner監視の観測処理（`hanjuku_narration.py`）。runtimeごとの非ブロッキングの
  ファイルロックで候補を1回だけ取り出し、最新の1件だけを既存の `enqueue_audio_text`
  （`hanjuku_commentary`）へデーモンスレッドで渡す。読み上げworker・共通音声は再起動しない。
- 抑止: 25秒のcooldown、同じ意味keyの連続、直近32件と同じ文、20秒より古い候補、処理中の重複、
  120字超。送信直前にも完全なruntime identity・終了状態・期限を再検証する。
  キューのsidecarへidentityとexpires_atを渡し、再生側でもclaim時・再生直前に照合して
  終了済み・別lease・期限切れを破棄する。結果は `hanjuku_narration.jsonl` に残す。
- ゲームオーバー時の振り返り実況（オーナー指示 2026-09-28）: `terminal_reason=='game_over'` の
  確定時に、当該ランの判断記録とラン状態だけから（第N章まで・獲得した城・出撃/戦闘回数・最終月・解雇回数を数えた）
  1行を `terminal_recap` 付き候補として `hanjuku_run.observe` 内で書く（実況の失敗で終了処理は塞がない）。
  terminal中は通常候補をすべて沈黙させ、この振り返りだけを `runtime_fence` なしで即時配信する
  （teardown中のidentity再検証・期限で落ちないため）。

## 改善用ログ

世代別の`run/runtimes/<runtime_id>/`へ保存する。ゲームを停止しても削除しない。

| ファイル | 内容 |
|---|---|
| `hanjuku_run.json` | bot版、世代、観測数、実入力数、戦闘開始/終了数、現在の判定、終了理由と根拠 |
| `hanjuku_events.jsonl` | 時刻、画面SHA-256、画面判定、実際に送信したボタンと押下時間、戦闘遷移、終了理由 |
| `hanjuku_events.previous.jsonl` | 4 MiBごとのローテート先。現行と合わせ最大約8 MiB |
| `hanjuku_frames/frame-*.png` | 画面判定の変化、60秒間隔、終了時の画像。120枚のリング |
| `hanjuku_frames/decision-*.png` | 名前確定・章確認・戦闘結果、将軍一覧・携行品選択/確認、いばら解除、切り札選択中/関連判断、代役選択・装備付き出撃開始に実際に使った画像。別の120枚リング |
| `hanjuku_bot.json` | botの現在の方策状態（チャート手順・占領・勝敗集計・所持金）。別世代へ持ち越さない |
| `hanjuku_decisions.jsonl` | 決定記録: `decision`、`chart_step`、`strategy_variant`、状況（画面種別・将軍・城・HP・所持金）、`deviation_reason`、`expected_metric`、`observed_metric`、`resulting_event`、`reason`、独自判断の原典戦術番号 `source_pattern`（①/③/⑥） |
| `hanjuku_commentary.jsonl` | 実況候補（文・意味key・生成元の決定・理由、または状況判定保留） |
| `hanjuku_narration.jsonl` | 実況の配信結果（enqueued/delivery_failed/skipped:理由） |
| `hanjuku_experience.json` | 状況キー別の独自判断実績（wins/losses）。世代をまたいで使用。gitignore済み`run/`配下 |
| `audio_volume.json` | ゲーム音声streamのsink・音量・mute実測 |

ログにLLMプロンプト、認証情報、ROM本体、セーブデータを含めない。画像と詳細イベントはVMローカルに保ち、
固定diagnosticsは許可されたphase、終了理由、入力数、戦闘回数、無変化秒数のみを公開する。
画像はリングで上書きされるため、イベントのSHAを使って対応を確認する。
`action_plan` は未送信の入力予定として記録し、実送信は `input_sent` だけで確認する。
両者を `decision_id` で結び、実際に判断に読んだ画像SHAと送信時の最新観測SHAは別フィールドに残す。
別leaseの方策状態から実入力の判断IDを推測しない。
再出撃の移動・将軍/装備選択・出撃確認は、元の `retry_context` の戦略名・逸脱理由・期待指標を
決定と `action_plan` に継承する。入力のない判定保留も理由を残し、読取不能を欠品と数えない。
出撃確認の空携行品は、実測した右欄の見出し・「きりふだは／ありません……」・承認文を
文字セルの位置まで照合する。欄外の背景を未知文字として拾っても、この一致を妨げない。
空表示が欠けた場合や、装備が必要な注文との不一致では承認しない。
非空の携行確認は、実機で得た1枚配置の見出し・カード名・空の残り行・承認文を
右欄の文字セルで照合する。複数枚は同じ既知カード枠に完全名が連続して並ぶ場合だけ
構造的に読み、チャートの枚数・種類と一致する場合に限って承認を予定する。
2/3枚配置の画面受入は別途実機で確認する。左欄のHP数字や背景は装備の数量と解釈しない。
未知文字や余分な文字、計画との不一致は承認せず保留する。
切り札選択も、実測したメニューの見出し・カード名・在庫数字・カーソル位置を照合する。
品切れで末尾の品目が消える表示を扱い、中間の欠落や未知の文字を品切れと推定しない。
対象カードの在庫0、未知の名前/数量、欠落行、未校正の複数桁表示は保留し、
選択予定を実所持や使用済みと数えない。

## runtime変更の確認項目

- registry/manifest: 既存`retroarch` adapterと世代別agent/game manifestを使用。新worker/queue/providerなし。
- health: 既存agent修復とcoordinatorのownership/lease確認を使用。別runtimeの終了証拠では停止しない。
- telemetry/diagnostics: 上記JSONLと`collect_diagnostics._project_corner_state`の固定射影。
  `bot_chart` は話数・チャート手順・占領数・勝敗/未分類・切り札消費・将軍損失・所持金・月だけを
  許可リストで公開し、文・理由・将軍名は公開しない。後続の semantic decision（#882）や
  終了後リプレイ比較（#838/#954）は `hanjuku_decisions.jsonl` の「状況・選択・結果」を入力にできる。
- regression: `tests/test_hanjuku_script.py`、登録、RetroArch境界、corner rotation、diagnosticsのテスト。
- deploy: docich protected mainの正規gateway経由。共有配信・音声を再起動せず、次回ゲーム起動から適用する。
- 実機受入: 新規ゲーム→入力→戦闘、終了後の復帰・子プロセス解放、配信PID維持を別々に検証する。
  ユニットテストや設定の有効化だけで実機受入の完了とはしない。

## 固定の手動起動操作

公開リポジトリでは汎用の`VM operations / exec`は拒否される。
ownerは`Corner rotation operator`の`start-hanjuku`と`confirm=production`を使用する。
protected mainとVMのSHA一致を検証し、ゲーム・コマンド・unitを入力できない固定scriptだけを送る。
ChatGPTのGitHub接続で新規workflow dispatchを利用できない場合は、固定Issue #1657へ
完全一致の`/hanjuku-start production`をownerが投稿する。専用workflowは同じowner・protected/current main・
production SHA一致を再検証し、同じ固定scriptだけを引数なしで実行する。任意ゲームや任意commandは受け付けない。
`docich-hanjuku-corner.service`が共通coordinator経由で起動し、現在試合の境界・pause・cooldownを守る。
要求の受理とゲームの実起動は別であり、`retro_corner.json`と世代別botログで実起動を確認する。
他のコーナーが稼働中の場合に強制停止したり、cooldown/stateを削除したりしない。

### 死んだruntimeの正規復旧（`recover-runtime`）

tmuxサーバ消滅などでgame/agentペインが死に、canonicalは`hanjuku-hero`をready/activeの
まま保持し、terminal evidenceが無い場合、通常のstop/switchは
`Hanjuku exited before terminal evidence`で拒否される。ownerは次の固定operation/CLIで
復旧する（ad-hocなrelaunchスクリプトを使わない）。

1. owner workflow `Corner rotation operator`の`recover-runtime`（`confirm=production`）を実行する。
   正規経路はこのworkflowまたは許可されたVMセッションの
   `bin/docich --config config/docich.soren-live.toml retro-corner recover-runtime`。
   - `retro_corner.json`がhanjukuのactive/failed、canonicalがreadyで`bot_identity`と
     完全一致する場合だけ動く。不一致は何も起動せず拒否する。
   - 共有session/displayを作り直し（`docich up`相当）、記録済みruntimeの
     `preflight`→`materialize_runtime`→`readiness`をアダプタ自身の契約で再実行する。
     ウィンドウが生きていればownership検証だけ行い、再作成しない。
   - その後、既存のoperator stop経路でセーブを試み、失敗時のみ`manual_forced_stop`を
     許可してコーナーを終了する。
   - cornerのtickが実行中（guard保持中）なら何も操作せずqueuedを返す。並行して
     `stop`を押したり、state/canonicalを手で編集したりしない。
2. 完了後、`corner-rotation-operator`の`recover-failed`でローテーションのラッチを解除する
   （既存手順。recover-runtime自身はラッチを解除しない）。
3. `retro_corner.json`のstatus、canonicalのphase/active game、ゲームウィンドウと配信フレーム、
   共通配信・音声PIDの維持を別々に実測する。コマンドの成功と実機復旧は区別する。

### 防衛戦の奥の手

- 卵を持つ通常敵が城へ攻め込み、実メニューで自軍の卵・切り札・退却が使えず奥の手だけ有効と分かった場合は、敵の召喚条件へ入る前に奥の手へ切り替える（v131、主人公も対象）。その時点で実行可能なチャートの札戦術を優先し、既存の安全な卵封じを妨げない。
- [防衛時の敵は思考パターン1](https://gcgx.games/hanjuku/ai.html)。壁ダメージ後の `HP < 話数+3` に対し、[壁ダメージ4](https://gcgx.games/hanjuku/battle.html)と直近の観測間ダメージを見込んでBを開く。接触位置や強い携行札でも早く召喚するため、HPだけで安全を保証しない。位置未校正の白兵待機が上限に達した場合も、この限定ルートを使う。メニュー開閉・認識待ちは有限回で、実際の奥の手のカーソルが読めた時だけAを送る。
- 灰色の「たまごをつかう」「きりふだ」「たいきゃく」が実位置に揃い、騎士カーソルを確認した場合は下へスクロールして「おくのて」を選ぶ。灰色の項目を使用可能扱いにはしない。
- 出現した3候補は[奥の手の効果順](https://gcgx.games/hanjuku/okunote.html)で最も有利なものを選ぶ。大臣アタック、もどき系、通常候補の順で、全候補が自傷の場合も最小被害の候補を選ぶ。画面のカーソルを確認してAを押し、選択を効果発生と混同しない。

### 主人公と将軍の緊急退却
