## 1. なぜ作り直すか

### 1.1 実測した現状（2026-11-03、main `d5f0adf18`）

| 事実 | 出所 |

### 1.2 構造上の原因

個別のバグではなく、次の三つが重なって同じ型の事故を出し続けている。

1. **観測の不確実さが分岐を増やす。** 所持金・カーソル・将軍の所在・HP を画面から推定するため、
   「読めない」「一時的に読み違えた」の分岐が手順ごとに生まれ、そのたびに待機・再確認・取消のキーが増える。
2. **手順の進行を毎観測で組み立て直す。** 「いまどの手順の何段目か」を明示的に持たず、
   画面種別と `mem` の断片から毎回推定する。古いキーの残留、別注文との取り違え、
   割込み後の復帰誤りがここから出る（例: #3245 残留 `sortie_attempt`、`reconciled sortie attempt` の取違え）。
3. **送信と成立の区別が弱い。** #3193 A で出撃だけは分離したが、月次・戦闘・家・帰還は未分離。

v1 の段階移行（`docs/hanjuku_state_redesign.md` 案）は 2 と 3 を挙動不変の整理で扱うが、1 は扱わず、
調停の連鎖も残る。並行して事故対応の修正が毎日入るため、移行は衝突しながら長期化する。

## 2. 目標と非目標

### 目標

- 第 1〜5 話を、無入力停滞・同一入力ループなしで進める（現行の到達点を下回らない）。
- 「どの手順が、どの段で、何を待っているか」が常に一つに決まり、記録から読める。
- 全ての待ちと再試行に上限があり、上限後の行き先（取消・やり直し・安全な画面へ戻る）が手順ごとに定義されている。
- 戦略（何をするか）を、記録した世界状態だけからオフラインで検証できる。

### 非目標

- 攻略方針そのものの変更。チャート・切り札表・卵の表（`hanjuku_chart.py`、`games/hanjuku-sfc-speedrun/data`）は流用する。
- 配信側の仕組み（コーナー、予想、実況、VM 配備）の作り直し。v2 は既存の CommandBrain 境界に収まる。
- v1 の改修。v1 は v2 への切替まで、事故対応の修正だけを受ける。

## 3. メモリ読取りの規則（可視性ゲート）

### 3.1 規則

オーナー決定を次の三つの条件に落とす。**三つ全てを満たす値だけ**を、判断に使ってよい。

1. **登録済みの項目である。** メモリ項目は「項目カタログ」（§3.2）に登録したものだけを読む。
   カタログにない番地は bot から読めない。
2. **その観測の画面に表示されている。** 項目ごとに「その値を表示する画面種別」を登録し、
   画素から判定した画面種別がそれに一致するときだけ、その観測で値を採用する。
   画面種別の判定は画素で行い、メモリには頼らない。
3. **画面の表示と矛盾しない。** 画面からも読める項目は、読めた場合に照合する。
   食い違えば、その観測ではどちらも採用せず、食い違いを記録する（不一致が続く項目はカタログを見直す）。

採用した値は、世界状態に「最後に見た値」として観測時刻つきで残す。
人が一度見た画面の内容を覚えているのと同じ扱いであり、表示されていない間にメモリから更新しない。

### 3.2 項目カタログ

項目ごとに次を持つ。カタログは一つのモジュール（`hanjuku_v2/perception/catalog.py`）に置き、
v2 のメモリ読取りは全てここを通す。

| 欄 | 内容 |
|---|---|
| `key` | 項目名（例 `gold`、`castle.owner`） |
| `address` / `length` / `decode` | 番地・長さ・復号（BCD、ビット列など） |
| `shown_on` | 値を表示する画面種別の集合（例 `gold` は月次メニュー・商人画面） |
| `screen_check` | 画面からの照合方法（照合しない場合はその理由） |
| `evidence` | 番地を同定した実測（日付・セーブ・画面と値の対応） |

可否の例（番地は未同定。§7 段階 0 で同定する）:

| 情報 | 可否 | 理由 |
|---|---|---|
| 所持金 | 可（月次・商人画面のとき） | 画面に数字で出る |
| 自軍将軍の HP・兵数・卵 | 可（将軍一覧・戦闘パネルのとき） | 画面に出る |
| 城の所有・位置 | 可（地図・Y 全体図のとき） | 旗・屋根が見える（位置は 0x1700 で同定済み） |
| メニューのカーソル行 | 可（そのメニューが開いているとき） | 手カーソルが見える |
| 話番号・年月 | 可（話の冒頭・ヘッダーのとき） | 冒頭の表示とヘッダーの年月 |
| 敵将軍の HP | 可（戦闘パネルに出ているとき）。出ていない間は不可 | 表示中だけ見える |
| 敵の行軍先・思考、乱数、隠れた能力値 | 不可 | 画面に出ない |
| 画面外の移動ボスの位置（第 9 話） | 不可 | 見えている間だけ可 |

### 3.3 強制のしかた

- メモリの生バイトは知覚層の外へ渡さない。戦略・手順には、ゲートを通った `Seen[T]`（値・出所 `ram|screen`・観測番号）だけを渡す。
- 層契約テストで、知覚層以外から RAM 読取り関数・生バイトを参照することを禁止する。
- 観測ごとに「採用した項目・画面種別・出所」を判断記録に残し、後から規則違反がないことを機械的に検査できるようにする。
- 評価器（§6）は判断に関わらないため、勝敗や到達話数の判定に非表示の値を読んでよい。評価器の出力は bot へ戻さない。

## 4. 全体構成

```
adapter.observe()  画面PNG + RAM読取り（前後2回）
      │
      ▼
知覚 perception    画面種別（画素）→ 可視性ゲート → Seen[...] の集合（Percept）
      │
      ▼
世界モデル world   Percept だけで更新。最後に見た値と観測番号。不明は不明のまま
      │
      ├──────────▶ 戦略 planner   決めどころでだけ呼ぶ純粋関数 → Goal / Order の列
      │                │
      ▼                ▼
実行 executive     手順スタック。担当は常に一つ。割込みは積んで、終わったら元へ戻る
      │
      ▼
入力記録 journal   送信の前に意図を保存 → 送信 → 次の観測で成立を判定
```

### 4.1 観測（adapter 側の追加）

- 既存の画面取得に、RAM の読取りを足す。順序は「RAM 読取り → 画面取得 → RAM 読取り」とし、
  前後で一致した項目だけを、その観測の値として扱う（読取りと画面取得は同時ではないため）。
- 読むのはカタログ項目を含む番地の範囲だけ。`send_ra_cmd` の受信上限（4096 バイト）に収まる単位で分ける。
- RAM が読めない（コマンド未対応、応答なし）ときは、画面だけで動く。v2 は RAM なしでも停止しない。
- Observation のスキーマに任意項目 `memory` を足す。v1 は読まないので影響しない。

### 4.2 知覚

- 画面種別と画面からの読取りは、v1 の OS 層（`os_layer/screen.py`・`phase.py`・`readers.py`・字形）を部品として流用する。
- 出力は `Percept`: 画面種別、その画面で見えている項目の `Seen[T]`、読めなかった項目の一覧。
- 知覚は状態を持たない（前回の観測を参照しない）。比較は世界モデルで行う。

### 4.3 世界モデル

- 型付きの値として持つ（辞書のキーではない）。章・月・城・将軍・資金・携行札・進軍中の部隊。
- 各値は `Seen` として観測番号を持つ。「不明」と「0」を区別する。
- 自軍の操作で起きるはずの変化（出撃した将軍が城から消える等）は、予測として別に持ち、
  観測で確認されるまで事実にしない（#3193 A の規則を全領域に広げる）。
- 永続化は版付き。読み込んだ版が未知なら手順を止めて理由を記録し、黙って初期化しない。

### 4.4 戦略

- 呼ぶのは決めどころだけ: 月初、出撃可能な将軍が城にいる、戦闘コマンドの選択、イベントの選択。
- 入力は世界モデル、出力は `Goal`（例: 「将軍 X を城 A から城 B へ、札 C,D を持って出撃」「卵回復を n 個」）。
- v1 の戦略層（`strategy/orders.py`・`kit.py`・`economy.py`）と判断層（`judgment/battle.py`）の判断規則を、
  世界モデルを入力とする純粋関数として移す。手順の都合（読めなかった、画面が違った）は戦略に入れない。

### 4.5 実行（手順スタック）

手順（`Procedure`）は段（`Step`）の列で、各段は次を持つ。

| 欄 | 意味 |
|---|---|
| `expect` | この段を始めてよい画面の条件（Percept に対する述語） |
| `act` | 送る入力（または入力なしで待つ） |
| `until` | 成立条件（次以降の観測に対する述語） |
| `limit` | 待てる観測数・再送回数の上限 |
| `on_limit` | 上限に達したときの行き先: この手順を取り消す／前の段へ戻る／安全な画面へ戻る手順を積む |

規則:

- **担当は常に一つ**（スタックの先頭）。v1 のように各手順へ「担当か」を問い合わせない。
- 予定外の画面は場面ルータが分類し、対応する割込み手順（戦闘、月初の場面、イベント文、はい／いいえ）を積む。
  割込みが終わると元の手順に戻り、元の手順は `expect` を確かめ直してから再開する。合わなければ取り消して戦略へ返す。
- どの手順にも合わない画面が続いたら、「安全な画面へ戻る」手順（B で地図へ戻る、を上限付きで）を積む。
  これだけが汎用の回復であり、未確認の決定（A）を汎用回復から送らない。
- 手順の状態（どの段か、何回待ったか）は手順の中にだけ持ち、手順が終われば消える。

### 4.6 入力記録

- `hanjuku_execution.py` の規則を出撃以外にも使う: 意図を保存してから送信し、送信結果を記録し、
  曖昧に終わった送信は自動で再送せず、次の観測で成立を判定する。
- 手順の `until` が「成立」の判定にあたる。成立しないまま上限に達したら `on_limit` へ進む。

### 4.7 常駐化

v1 は 1.5 秒ごとにプロセスを起動して状態ファイルを読み書きする。v2 は世界モデルと手順スタックをメモリに持つため、
常駐プロセスとして動かす方が単純で速い（#2832）。ただし CommandBrain 境界は変えず、
最初は v1 と同じ起動方式で動かし、常駐化は段階 3 以降に別変更で行う。

## 5. v1 から流用するもの・しないもの

| 流用する | 流用しない |
|---|---|
| 字形・画素読取り、画面種別の判定（OS 層） | 調停の優先連鎖（`orchestrator.py`） |
| チャート・城座標・切り札表・卵表 | `mem` 辞書とそのキー |
| 戦略・判断の規則（純粋関数に移して） | 手順層（`flows/*`）の実装。手順は §4.5 の形で書き直す |
| `hanjuku_execution.py` の送信規則 | 個別事故ごとの hold/miss/recheck キー |
| 実測した画面の事実（docs の各実測記録、テストの実画面 fixture） | |

v1 の事故記録とテストの実画面 fixture は、v2 の手順を書くときの仕様として読む。
v1 が個別に塞いだ事故のうち、v2 の構造で起きなくなるもの（残留キー、担当の取り違え）と、
v2 でも手順の `until`/`on_limit` に書く必要があるもの（ゲーム側の特殊な画面）を分けて扱う。

## 6. 検証

| 種類 | 内容 |
|---|---|
| 知覚の照合 | 本番の記録（画面 + RAM）を再生し、画面読取りと RAM の値の一致率を項目ごとに測る |
| 規則の検査 | 判断記録から、表示されていない画面で RAM 値を採用した観測がないことを機械的に確かめる |
| 戦略の単体 | 記録した世界モデルを入力に、Goal を固定する |
| 手順の単体 | 実画面 fixture の列で、成立・割込み・上限到達・再起動を表で検証する |
| 実 ROM での通し | 隔離 libretro ハーネス（VM の既存プローブ）で、セーブから v2 を走らせ、到達話数・停滞・ゲームオーバーを数える。評価器は RAM の全体を読んでよい（§3.3） |
| 本番での並走 | 切替前に、v1 が操作する本番ランで v2 の知覚と世界モデルだけを動かし、入力は出さずに記録を比べる（影モード） |

合成した画面だけのテストで「動く」とは判定しない。

## 7. 段階

各段階は独立に PR・配備する。v1 はどの段階でも本番の操作を続け、v2 が本番の入力を出すのは段階 4 から。

### 段階 0: 実現性と RAM 番地の同定（入力なし）

- 本番とは別の RetroArch を VM で起動し（隔離、`nice` + `timeout`）、`READ_CORE_MEMORY` が
  RetroArch 1.18.0 と snes9x コアで使えるか、応答時間を測る。使えない場合は RAM なしで進む（§4.1）。
- 隔離ハーネスで、画面に出る値（所持金、将軍の HP・兵数・卵、メニューのカーソル、月）を変えながら、
  RAM の差分から番地を同定し、カタログに `evidence` つきで登録する。
- 完了条件: 主要項目（所持金・自軍将軍の HP/兵数/卵/所在・城の所有・カーソル・月・話）の番地と、
  `READ_CORE_MEMORY` の可否が実測で決まっていること。

### 段階 1: 知覚と世界モデル（入力なし）

- adapter に RAM 読取りを足し（§4.1）、v2 の知覚・世界モデルを書く。
- 本番で影モードとして動かし、画面と RAM の一致率、世界モデルと v1 の認識の差を記録する。
- 完了条件: 主要項目の一致率と規則検査の結果が記録で示せること。

### 段階 2: 実行の骨格と第 1 話（隔離ハーネスのみ）

- 手順スタック・場面ルータ・入力記録・安全な画面へ戻る手順を書く。
- 第 1 話に必要な手順（名前入力、先発隊、出撃、戦闘、月次の購入・兵の補充、卵回復）を §4.5 の形で書く。
- 完了条件: 隔離ハーネスで第 1 話のクリアを、複数回の実走で停滞なしに示すこと。

### 段階 3: 第 2〜5 話（隔離ハーネスのみ）

- 帰還・家での修理・特殊ボス（第 4 話の四季王、第 5 話）など、残りの手順を足す。
- 完了条件: 各話のセーブから隔離ハーネスで、v1 の到達点以上を停滞なしに示すこと。

### 段階 4: 本番切替

- 版選択で v2 を本番に出す。停滞を検知したら v1 に戻す自動の切替を残す（緊急停止用。人の確認工程ではない）。
- 挙動変更は既定で有効にして出す方針に従い、切替の PR のマージが本番適用となる。
  適用後は配備・VM HEAD・観測された版の切替まで確かめる。
- 完了条件: 本番の連続 3 ランで、v1 以上の到達と停滞なし。

### 段階 5: v1 の撤去

- v1 への自動切戻しが一定期間起きなければ、v1 の手順層・調停・互換ファサードを削除する。

## 8. 並行作業との関係

- #3193 C（v1 の状態の所有者分離）は v2 と目的が重なるため、v2 の段階 2 の結果を見るまで新しい範囲を始めない（オーナー判断待ち）。
- v1 への事故対応の修正は続ける。ただし v1 の構造を広げる修正（新しい調停の分岐・新しい共有キー）は最小にする。
- 未マージの v1 PR と v2 は別のファイルを触るため衝突しない。v2 は `src/docich/hanjuku_v2/` と `brains/hanjuku_v2/` に置く。

## 9. 未決・未確認

- `READ_CORE_MEMORY` が本番構成で使えるかは未確認（段階 0）。
- 画面に出る値の番地は、0x1700（城表）・0x1600（話番号）・0x1611（年）以外は未同定。
- 「画面に表示されている」を、その観測の画面に出ている場合に限る（§3.1 の 2）。
  別の画面を開けば見える値（例: 将軍一覧を開けば分かる HP）を、開かずにメモリから読むことは、この設計では不可として扱う。
  オーナーの規則の読み方として緩める場合は §3.1 を改める。
- 影モードの CPU 負荷（#2790・#3114 の音切れと関係する）は段階 1 で測る。
