# 戦線位置校正の進捗（Issue #1180 / Phase 1a）

Phase 0はPR #1190、HP遮蔽修正のPhase 1aはPR #1194で配備済み。後者はmain `5826e763`、`hanjuku-chart-v14-visible-hp`。同じg403・ゲーム/共通配信PIDを維持したホットロードと実戦の白兵判断を確認した。Phase 1の位置制御の校正は続行中で、`front_x`、ASSIST_PULSE、COAST、位置閾値や話数マージンはまだ導入しない。

## 観測方法

2026-09-27、既存ゲームの299×224窓を変更せず観測した。通常の判断と画像hashが一致する54枚を保存し、別途同じ小窓を20fps・12秒ずつ3回撮影した（合計720枚）。撮影は時間制限つき・単一threadの別プロセスで、入力・pause・restart・配信エンコーダ操作は行っていない。解析では既存の `Frame.resized()` で256×224に正規化した。ROM内部メモリは参照していない。

元画像はignored `run/hanjuku-1180-front-evidence/` 内。ゲーム画像・ROM・save stateはGitに含めない。通常判断の記録は実際の入力計画に対応するが、20fpsの追加撮影は独立した観測なので、各フレームに対してbotが判断・操作したとは扱わない。

## 実測で見つかった不具合

飛ばされた兵士がHP欄に重なる。`TextLine.words()` は未知glyphを区切りとして読み飛ばすため、十の位が欠けた「32」を、読めた一の位だけの「2」として返していた。

- `rapid/batch-1/frame-0016.png`: ミントの表示HPは32だが、兵士が十の位に重なり旧parserは2を返す。HP欄には兵士の緑 `(57,165,123)` 等が混入。
- `rapid/batch-1/frame-0018.png`: 兵士が外れ、同じHP32を読める。通常のHP背景は `(238,238,238)`、字色は `(32,32,32)`。
- `rapid/batch-2/frame-0021.png`: コリアンダーのHP28も同様に2として読まれる。
- `risk-rapid/batch-1/frame-0004.png` / `frame-0033.png`: クミンの読み取りも2 / 1へ落ち、後続フレームで元に戻る。

これらの欠けをダメージと扱うと、`after_clash`、低HPの救命・どうしの退却に誤った根拠を与える。後続のHP上昇で帳尻を合わせても、送った入力は取り消せない。

## Phase 1aの変更

人間白兵パネルの実測したHP枠（敵x=88..111、味方x=216..239、y=176..183）全体を検証する。RGBが等しい背景/文字のみ、3セル右詰めで1〜3桁、未知glyph・桁の穴なしの場合だけ受理する。色のついた兵士が空白セルに重なっていても、隠れた百/十の位がないと証明できないため未分類にする。枠外の4桁を3桁に切り詰めない。

重なり時はパネルを読取り不能とし、既存の最後の確定HPを保持して無入力にする。次の見えるフレームで復帰する。待機フレーム数を新設せず、推測によるHP補完も行わない。エグモン用の別パーサー、メニュー操作、カード優先順は変更しない。

これは**HP欄の実測座標**であり、戦線位置・卵発動の安全境界の校正値ではない。

## 保存画像の再生比較

各セット240枚について、両将軍名がそのセットの対象と一致するパネルを比較した。

| 対象 | 旧parserが受理 | 修正後が受理 | 敵HPが一度低く読まれた後に上がる回数（旧→修正後） |
| --- | ---: | ---: | ---: |
| ミント対どうし | 55 | 43 | 1 → 0 |
| コリアンダー対ヴィーナス | 208 | 190 | 1 → 0 |
| クミン対どうし | 50 | 47 | 2 → 0 |

回数は受理した隣接パネルの比較で、真のダメージ量・全フレームの正解率を保証するものではない。v14でマカデミア戦の白兵判断が進むことは確認したが、遮蔽中の無入力を本番の同一フレームと突き合わせる検証はまだない。誤読4画像を分類差替えなしの `decide()` に再生すると、いずれも無入力になる。合成テストは同じ枠・paletteで欠け方を再現し、1/2/3桁・HP0、各セルへの兵士色、未知glyph、一の位消失、完全に隠れた十の位、枠外4桁、正常HP保持、無入力を検証する。

## 位置制御に残る校正

稽古では将軍が接触後に大きく離れる。通常戦では同じ色の兵士が複数おり、HP欄の上にも飛んでくる。単なる色の重心・左右全体の中間点を将軍の接触帯と認定できない。

クミンの卵使用場面も撮影できたが、将軍同士の接触位置が原因なのか、壁・開幕など別の判定なのかをこの画像だけで確定していない。Phase 0のHOLDでも自然な前進や他の卵判定は残る。

次は敵味方の**将軍だけ**の位置を、接触/離反/兵士の遮蔽/召喚開始のフレームごとに注釈し、将軍の識別と接触判定の独立検証を行う。その後にparserのraw `front_x` / confidenceとpolicyのzoneを分離して実装する。章別安全域と壁ダメージ前後の条件も未校正であり、現時点では推測した閾値やASSIST入力を有効にしない。

## rollback

このPhase 1a PRのみをrevertできる。永続状態の移行はなく、Phase 0の敵卵トリガーとHOLDは維持される。ただしHPの欠けを低HPとして扱う旧挙動に戻る。新paletteや別layoutでは読取り不能になる可能性があるため、追加の実画面で受理範囲を広げる際も未校正を成功扱いしない。


## 追加の60fps観測と接触していない例

同じ299×224窓・同じg403で、ガルバンゾー対どうしとラズベリー対アルファルファを各8秒・60fpsで受動撮影した（v13、HP修正の配備前）。待機上限300秒・各1threadで2回、終了後に子プロセスも終了した。描画解像度を上げず、入力・pause・restartは行っていない。

`contact60/batch-1` と `batch-2` は各480枚。PNG内容の異なる画像は362枚と354枚なので、60fpsで取得したことをゲームの60fps更新の証明とは扱わない。追加960枚を含め、正本画像は上記ignored evidenceディレクトリに保存する。

[`fixtures/hanjuku_front_negative_annotations.json`](fixtures/hanjuku_front_negative_annotations.json) に9枚の画像SHA-256と、敵味方の将軍を囲む矩形を記録した。256×224への正規化には既存の `Frame.resized()` を使い、矩形を重ねた画像を目視確認した。矩形は将軍の所在範囲であり、厳密な輪郭・接触点・ゲームの安全閾値ではない。未提供の原画像を合成画像で代用して実画像検証済みと扱わない。

この9枚はすべて**接触が見えていない例**で、`front_x` はnullとする。主な否定例は次の通り。

- `passive-final/000172.png` / `000174.png`: 両HPが減少していても将軍は離れている。HP減少や `clashed` の履歴から、その画像の接触位置を復元しない。
- `risk-rapid/batch-1/frame-0040.png`: 二人が近づいているが、まだ間が空いている。二人の中点を実際の接触点と認定しない。
- `risk-rapid/batch-1/frame-0060.png`: 敵の卵使用告知があるが、その時点では二人は離れている。告知時の中点から卵判定の閾値を決めない。
- `contact60/batch-1/frame-0120.png`: 兵士が飛ばされていても将軍同士の接触とは限らない。

実装の次のゲートは、接触が見える正例、遮蔽して不明な例、複数の将軍外見・背景について独立に確認できるラベルを揃えること。現在の9枚だけで接触検出の感度や誤検出率を保証しない。runtimeはこのJSONを読み込まず、Phase 0のHOLDを維持する。
