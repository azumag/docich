# 章末ボスの波状攻撃が行軍中に止まる（v382、2026-11-04）

## 症状

全通常城を制圧して残り目標がボスだけになった場面で、ボスへの出撃が
行軍中の間、新しい出撃が計画されない時間ができる。フィールドのマップで
入力を返さず、判断ログには `chart_interim_hold`（奪還・攻撃・移動の
いずれも作れない）が残る。

g1133（第5話、2026-11-04）の実測:

| 時刻 (JST) | 出来事 |
| --- | --- |
| 16:18:37 | アテナをボスへ出撃（`order_launched`） |
| 16:19:40 | 別のボス出撃（ヴィーナス）が部隊▲未観測でロールバック |
| 16:19:41 | `chart_interim_hold`（候補0件） |
| 16:22:57 | 次のボス出撃（ヴィーナス）を開始 |

## 原因

2026-11-02 の設計（ボス城へ余剰兵力を連続投入）は `interim_candidates`
でボスを `targets` に追加し、`_boss_wave_pick` で最も強い余剰を選ぶ。
しかしその後段の「同じ目標への出撃は1件だけ」ガード

    targets = [c for c in targets if c not in heading]

がボスにも適用され、`heading`（`SORTIE_BUSY_TICKS = 400` 観測、約10分）
に入っている間はボスが候補から消える。章末はボス以外の目標が無いため
候補が0件になり、`map_step` は入力を返さず実時間を待つ。

## 修正（v382）

- ボスだけ `inflight` / `heading` の除外を免除する（`_boss_wave_open`）。
  他の目標は従来どおり1件ずつ。
- 同時に飛ばす上限は他の目標と同じ波予算（`1 + INTERIM_WAVE_LIMIT` = 5）。
  余剰将軍と「城に1人残す」規則は従来どおり候補を絞る。
- 2隊目以降の step id に将軍を含める。出撃元と目的だけの id では、
  1隊目の行軍中に作った次の隊が同じ step 名になり、`launched` のまま
  再発行されないため。1隊目は従来どおり位置に依存しない id を保つ。

## 確認の仕方

- `bot_version` が v382 になったあと、章末のボス行軍中に
  `chart_interim_hold` が記録されず、`sorties` にボス行きの行が
  連続で増えること。
- `tests/test_hanjuku_boss_wave_double.py` が、行軍中でも次のボス隊を
  計画し、上限では止まり、通常城の1件規則を変えないことを確認する。
- 実プレイでの成立はデプロイ後の実観測で確認する。テストとCIの成功を
  実機の成立とは扱わない。

## 追記（v383）: 発射未確認で failed になったボス指示の再武装

v382 を配備したあとも、g1133 では 16:22 から 40 分以上ボス出撃が
計画されなかった。原因は波の上限ではなく、16:18 のアテナ出撃で部隊▲を
観測できず、16:22 に `LAUNCH_MISS_LIMIT` で同じ step が `failed` に
なったこと。機械計画は同じ request id のまま毎観測その step を出し直すが、
`next_order` は `failed` を飛ばすため、再計画だけが繰り返されていた。

v383 はボスの step に限り、月内3回・100観測（約2.5分）間隔の上限付きで
`pending` へ戻す（`_rearm_failed_boss_steps`、`plan_step_rearmed` を記録）。
通常の ready・出撃元・携行の検査はそのまま通す。到達できないボスを
無限に叩かないための上限であり、月が変われば回数は戻る。

## 追記（v385）: 奪還が失敗し続ける城がボス出撃を止める

v384 まで配備された g1133 では、17:44 のボス出撃を最後に 18:50 時点まで
ボスへの新しい出撃が出ていない（`order_launched ... ボスへ出撃` が 17:44 で
止まる）。この間の出撃は、クロチェット（17:48 に全体マップの旗が敵色になり
失陥）の奪還と、兵の移動・守備の厚み付けだけだった。

実測（VM の `hanjuku_bot.json` を取得して `interim_candidates(mem)` を再生）:

- `lost = ['クロチェット']`、他の通常城は全て自城。アルマムーンに将軍が8人。
- 候補は `retake_*`（クロチェット）と `move_*` だけで、ボス行きが0件。
- 計画の同城向け奪還は `failed` が3件（`sortie_launch_failed`、部隊▲を観測できない）。
  アルマムーンからの行軍は途中のオトラントに吸収され、オトラントの唯一の
  将軍は残すため、発射元の切り替えも効かない。

### 原因

機械計画のボス波状攻撃は「ボス以外の全城が自城」のときだけ `targets` に
入る（`boss_path` が全通常城）。1城でも失陥し、その奪還が発射できないと、
ボスは永久に候補へ入らず、余剰の将軍は本拠地に座ったままになる。

### 修正（v385）

- 城ごとに、計画内で `failed` になった奪還 step を `retake_failures` に
  記録する（`_off_chart` の冒頭、計画が破棄される前）。奪還できた城・別の
  章の記録は捨てる。
- ボスを塞いでいる未所有の城が全て「失陥済み、かつ奪還の失敗が
  `RETAKE_STALL_FAILS`（3件）以上」なら、ボス波状攻撃を候補へ入れる。
  失陥していない未占領の城が残っていれば従来どおり待つ。
- 止まっている奪還は先頭枠を占めず、ボス波が先頭、奪還は後ろの通常候補へ
  回る（奪還が成立する機会は残す）。

### 確認の仕方

- `bot_version` が v385 になり、`chart_adjust_applied` の直後に
  `order_start`（`暫定: ...でボスを攻撃`）と `order_launched ...ボスへ出撃`
  が出ること。ボス行きの `sortie_launch_failed` が続く場合は別原因
  （発射確認の ▲ 判定）として扱う。
- `tests/test_hanjuku_boss_wave_double.py` が、失敗が閾値未満なら待ち、
  閾値以上で解除し、計画が失敗 step を落としても保たれ、奪還できた城では
  忘れることを確認する。
- 実プレイでの成立は配備後の実観測で確認する。テストの成功を実機の成立とは
  扱わない。

## 追記（v386）: 第6話の全体マップ（Y）が読めず出撃先に進めない

Y 画面は全て1008、それ以外のフレームは10未満。

### 確認の仕方

- 配備後に `y_jump_unknown_hold` が出なくなり、`y_jump_confirm` と
  `order_launched` が続く。`world_map_owners` が第6話でも記録される。
- 旗が敵色の城を bot が失陥扱いにして奪還へ回すため、第6話の占領数が
  一時的に減って見えることがある（実際の所有に合わせる動作）。
- `tests/test_hanjuku_world_map_sea_cursor.py` が、実機の採取画像
  （299幅→256幅へ縮小）で認識・カーソル・旗を確認する。
- 実プレイでの成立は配備後の実観測で確認する。

## 追記（v387）: 切り札は不利でなくても開幕で使う

オーナー指示（2026-11-04）:「きりふだはピンチのときではなく、状況を有利に
するためにつかうものなので、不利な状況でなくてもつかうようにしてほしい」。

### 実測（g1133 第6話、21:48〜23:19 の判断ログ）

- 25戦のうち切り札を選んだのは3戦。`battle_card_damage_rejected` は14件で、
  ほぼ全て クースカン（敵HP半減）が `control_has_no_observed_followup`。
  22:45 のコリアンダー対エシャロット（自38対敵46）は、36秒間に6回
  「開く→拒否→白兵に戻る」を繰り返し、札を使わないまま退却した。
- 携行した強い切り札の開幕使用は `strong_only` で、`_strong_enemy` が
  「強い将軍」と判定した戦闘以外では温存していた。

### 変更（v387）

- 携行した強い切り札は、敵が強い将軍でなくても開幕で使う。強さの判定は
  `battle_card` の記録に根拠として残すだけで、使用の条件にしない。
  ボス専用札（`boss_only`）と、使用済みの札を再度使わない規則は変更なし。
- クースカン（半減）は、後続の攻撃札が一覧に無くても、半減後の敵HPが
  自分のHP以下になるなら開く（`halving_not_a_kill`）。ボスと HP 未読は
  従来どおり拒否。使用後の白兵追撃（`control_then_melee_not_a_kill` の
  `_control_melee_advantage`、HP2倍・兵数・戦闘力の条件）は変えない。

### 確認の仕方

- 配備後、`battle_card` の理由が「出撃時に携行した強い切り札を強い将軍へ
  開幕で使う」で、弱い将軍相手の戦闘にも出る。`battle_card_damage_rejected`
  の `control_has_no_observed_followup` が減る。
- 未確認: 札の使用告知の署名が未校正（`battle_card_candidate`）のため、
  使用後に同じ札をもう一度選ぶ（`battle_card_announce_retry`）ことがある。
  23:18 のコリアンダーは1回目で敵HP 55→28 に半減したのに2回選択した。
  これは本変更では直していない。

## 追記（v389）: キャンプ帰還は取り消さず指定する／有利なのに卵を使う

### 1. キャンプ帰還の帰還先指定（オーナー指示 2026-11-05）

「キャンプ帰還、全体マップで城の指定に失敗してキャンセルになったので修正して。
最悪キャンセルにせず、どこでも良いから指定する」。

実測（g1133 00:14:20〜00:14:49）: きかん→全体マップの帰還先ピッカーで、
ダーラントを目標にカーソルを動かしたが、読み取ったカーソルが
(111,62)→(91,80)→(129,80)→(175,90)→(73,120) と城から城へ跳び、最後の
(73,120) で `right` を8回押しても動かず `camp_recall_aborted
picker_cursor_stationary`。撤退した将軍は野営のまま帰れない。

- ピッカーのカーソルが動かない（`PICKER_STILL_LIMIT`）／観測が上限に達した
  ときは、取り消さず、カーソルがいる城で A を2回送って確定する
  （`camp_recall_picker_fallback`）。城の上にいなければ、その位置でも1回確定する。
  以後は既存の `_recall_dispatch_step` が有限回で結果を確認する。
- 例外: 全体マップの旗が敵色の城の上にいるときは、従来どおり確定せず取り消す。
- 野営の帰還先画面（`map_target`）で自城の屋根が見えない場合も、敵屋根が
  マーカー付近に無ければ、マーカーの位置で一度確定する（マーカーが無いときは取消）。

### 2. 有利なのに卵を使う

実測（g1133 23:23:20〜23:23:22）: ヘスティア（HP25/25, 戦闘力9）対ヘーゼル
（HP33, 戦闘力4）。HP×戦闘力は 225 対 132 で有利だが、兵数が未読
（`card_soldiers_current` False）のため全ての卵温存規則が成立せず、
衝突前の救済メニューで「たまごをつかう」を選んだ。

- 兵数が両軍とも未読のときは `_melee_balance` が両軍ともHPだけで評価する
  （どちらにも兵数を加算しない公平な比較）。この比較で自軍のスコアが敵の
  1.5倍以上、自軍が最大HPの7割超で、強い将軍・主人公・召喚戦ではないときは
  卵を温存する（`_hp_only_clear_margin`）。
- 温存は一方通行ではない。救済メニューは毎パネル再評価するため、HP低下・兵数の
  読取・召喚があれば直ちに卵を使う側へ戻る。
- 召喚戦（敵が卵で召喚獣を出した後）の卵使用は変更なし。敵召喚獣のHPが
  自軍の1.4倍以上（`enemy_monster_threat`）のときに使うのは従来どおり。
  g1133 の 23:07/23:12/23:24 の3件はこの規則（召喚獣HP 192/119/289 対 自軍 85/63/25）
  で、卵の無駄遣いとは判断していない。

### 確認の仕方

- キャンプ帰還: 配備後、`camp_recall_picker_fallback` → `camp_recall_requested`
  が出て、`camp_recall_aborted picker_cursor_stationary` が出なくなる。
  実際に将軍が城へ戻るかは `camp_recall_unconfirmed` の後の所在で確認する。
- 卵: 兵数未読で有利な戦闘に `battle_egg_conserve`（conservation.rule
  が `hp_only_clear_margin` ではなく従来表記のままの場合あり）が出て、
  `battle_survival_select` の `たまごをつかう` が減る。

## 追記（全体マップ失敗の記録が永久に残りボス出撃が止まる）

2026-11-05 の実測（g1133 第6話、全11城占領後）: 09:02〜11:12 の2時間、`order_start`・
`order_launched` が0件。有効な指示は「トレビス オケアナ→ボス」で、判断ログの
`y_jump_open` は別の古い指示（アルブラーカ→ボス、`M97e81e`）に対し毎回
`attempt: 1` で2分おきに出るだけだった。

- `y_jump_last` が `{'step': 'A:bf8c3dee:M256898', 'mode': 'map',
  'moves': 3, 'why': 'cursor_stationary'}` のまま残っていた（05:14 の失敗。
  冬の地図で雪を静止したリングと誤読した疑い。月は未確認）。`_want_y_jump`
  は「同じ指示で直前のジャンプがカーソルを動かせず閉じた」場合は Y を使わず
  歩く規則で、この記録は指示を作り直さない限り消えない。
- 歩く経路は位置推定が [392,144]（本城）で凍結し（`map_no_cursor` の計数、
  v433 の調査対象）、出撃元のオケアナへ着けない。結果、Y も歩きも使えない。
- 毎観測の計画再構築で有効な指示が入れ替わり（`plan_stale_rebuild`）、Y ジャンプが
  毎回1回目からやり直しになる問題は別に残る（本変更の対象外）。

### 変更

閉じたジャンプの記録に `tick` を持たせ、`Y_JUMP_BLOCK_TICKS`（200観測、約5分）で
ブロックが失効する。`tick` を持たない旧状態の記録は最初に見た時点で刻印し、そこから
数える。指示ごとの上限（`Y_JUMP_LIMIT`）と全体の上限（`Y_JUMP_TOTAL_LIMIT`）は
そのまま。

### 確認の仕方

配備後、約5分以内に `y_jump_open` が有効な指示（トレビス→ボス）の step で出て、
`y_jump_confirm`・`sortie_departure_requested`・`order_launched` へ進む。進まなければ、
次の原因（計画再構築による指示の入れ替え、歩行経路の位置凍結）を調べる。


## v441 野営の帰還: 失敗した野営を1つしか覚えず2つで往復していた (2026-11-05)

- 実測 (g1133 第6話 14:16): 野営 `[52,148]` と `[11,46]` が交互に `camp_found`→失敗を数秒おきに繰り返し、
  ボス注文に必要な地図の短い時間 (約20秒) を食っていた。
- 原因: `recall_skip` が直近の失敗1件の単一枠で、A失敗→B選択→B失敗でAの保留が外れ、またAが選ばれた。
- 変更: 失敗した野営ごとの保留を `recall_skip_history` に最大6件残し、各自の窓が切れるまで除外する (章ごと)。
- 未確認: 出撃頻度が戻るか。防衛戦の頻度 (本城への攻め込み約6分おき) のほうが効いている可能性も残る。
