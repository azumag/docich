# ボス候補セルを隊ごとに並列で試す（v404、2026-11-05）

## 背景

v402 の実測で、ボス城へ向かった軍は出撃元の名簿から消えており（出撃成立）、
チャートのボスセル (818,184) は Y ビューの基地中心と 1px 以内で一致していた。
それでも 1634 観測（約27分）入城しなかった。

v403 では「入城できないまま出し直し上限に達したら候補セルを1つ進める」逐次方式にしたが、
候補は5つあり、1候補あたり約27分（1600観測）かかるため、全候補の掃引に約2時間必要だった。
また同時に6〜8隊が行軍しているのに、全隊が同じセルを狙っていた。

## 変更（v404）

- 候補セルの割当を「章」から「指示（step）」へ移した。
  `mem['boss_step_probe'][step] = 候補番号` を `_adopt_plan` で新規ボス指示に順番に割り当てる
  （0 → 1 → 2 → … を候補数で循環）。
- `navigation.boss_probe_cell(mem, name, step)` は指示の候補番号を使う。
  候補番号のない指示・ボス以外の城・候補表のない章はチャートセル。
- 逐次シフト（v403 の `_shift_boss_probe` と `boss_cell_probe_shift`）は撤去し、
  出し直し上限の挙動は v402 以前に戻した（上限で `boss_relaunch_exhausted`）。
- 割当表は新しい40件だけ保持（無限に増やさない）。

## 期待する効果

同時に行軍している複数のボス隊が、それぞれ別の候補タイルを試す。
1回の行軍窓（約27分）で最大5候補を並行して試せるため、逐次方式の約2時間に対して約1/4の時間で当たりを引ける。

## 検証

- `tests/test_hanjuku_boss_cell_probe.py` を新設計に書き換え（6件）:

  狙いは指示ごと／通常城は対象外／割当は40件で有界。
- 層テスト `test_hanjuku_layers.py` と `test_hanjuku_boss_sortie_overdue.py` を含め 46 passed。
