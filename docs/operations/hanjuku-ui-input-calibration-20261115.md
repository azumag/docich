# 半熟英雄の一覧・数量入力のローカル校正（2026-11-15）

## 環境と再現方法

既存のローカルROM `games/roms/hanjuku-hero.sfc` と隔離環境の保存状態を、
Snes9x libretro 1.63 (`fae2fea`) へロードした。ROM・保存状態・コアはGitに追加しない。
コアのSHA-256は `8ed333ac04544cc6ab67ceb445d095f7600bb17586d4887d99117fbd1ef776f6`。
本番のゲーム・配信プロセスや保存状態には入力・書き込みを行っていない。

既存のローカル `tmp/hanjuku-local/core_driver.py` のCoreと画像コールバックを使用し、
bot runner・autosave・runtime更新は呼ばず、メモリ上のコアだけを操作した。
各比較は同じ保存状態を再ロードし、方向キーを6フレーム押して解放し、無入力で再観測した。
一覧の連続入力は6フレーム押下・3フレーム解放を4回とした（100ms/50ms相当）。
画面を取り直し、実カーソルと文字列で移動結果を確認した。
メニューを最初に開いた直後は初回の方向入力が移動にならない場合も観測したため、
送信したキーの回数を到達証拠にはしない。

## 実装の境界

卵回復・砦・部分的な将軍再確認・先発隊の上段について、現カーソルから目標までの
全行が一意に読める場合だけ連続入力する。卵回復の全回復y47と最初の将軍y71の間隔は
通常の16px行と異なるため、明示した行順で数える。先発隊は既存の3入力/バーストと
9入力上限を、連続入力中の実入力数で消費する。選択済みで暗転した上段の行や欠落行を
経路として使わない。全名簿の巡回、未表示の名前の探索は従来の1行ずつの観測を維持する。

商人はy183の数量・合計金額の固定文とy199の問い、桁と手カーソルが同じ画面で読める場合だけ、
単発100msの上下・有効な桁移動の再観測周期を1500msから500msにする。
この読みは数量・価格・購入完了の新しい証拠を作らず、購入判断や支払い照合には使用しない。
A/B、長押し、複数入力、未読・曖昧な画面は通常周期を維持する。

実ゲーム全体の時間短縮率と本番への反映・効果は未測定。

## 追補: 第8話の先発隊での入力受付

既存のローカルSRAMからセーブ1（第8話「かんじゅく だいしょうぐんの やぼう」の
最初から）を通常のCONTINUE/ロード確認で開き、先発隊画面へ到達した。
SRAMやゲームRAMの内容は改変していない。ROM・コアは初回と同じで、bot_versionも
`hanjuku-chart-v852-visible-menu-batches` のままである。

上段の4人は、ヴィーナス（y47）、アテナ（y63）、ミルフィーユ（y79）、
フェデリーニ（y95）。下段は空。この読める画面を作業用の保存状態にし、各試行で
復元して映像更新用の4フレームを進めてから、以下の追加待機を入れた。

|追加待機（フレーム）|入力|入力開始から約500ms後の実カーソル|
|---:|---|---|
|0|Down 100ms ×3、間に解放50ms ×2|フェデリーニ（y95）|
|5|同上|フェデリーニ（y95）|
|15|同上|フェデリーニ（y95）|
|30|同上|フェデリーニ（y95）|
|60|同上|フェデリーニ（y95）|
|90|同上|フェデリーニ（y95）|

各試行は押下6フレーム×3と解放3フレーム×2の合計24フレームを送り、さらに6フレーム
無入力で進めて再観測した（60.1fpsで約500ms）。予定入力の回数ではなく、実画像の
手カーソルと選択行を照合した。これは読める画面からの試行であり、フェード中の受付や
他のROM/コアまで保証するものではない。

下段が空のまま最下段へ移動した状態から、実際の `starter.step` も実行した。

1. ヴィーナスを選ぶUp 3回を返し、`pending`も下段の人数も増えない。
2. 約500ms後の実カーソルがヴィーナスへ戻った画像でAを返す。ここでは`pending`だけが立つ。
3. A後は既存の1500ms周期を使い、下段y119のヴィーナスと、暗転した上段先頭を実画像で確認する。
4. アテナ、ミルフィーユも同じく実下段への追加を確認し、3人が並んだ最終確認でAを返す。

今回の入力では取りこぼしや誤選択は見つからず、動作コードの変更は不要だった。
最終確認後の次章プレイ進行、城への到着、ゲーム全体の速度改善は検証対象外。

未加工の実フレームを以下のfixtureとして追加した。

- `local-starter-top.png`: Up 3回後の上段先頭、下段0人。
- `local-starter-bottom.png`: Down 3回後の上段最下段、下段0人。
- `local-starter-one-selected.png`: A後、下段にヴィーナスが追加され上段先頭が暗転。
- `local-starter-three-confirm.png`: 下段3人と最終確認。

`tests/test_hanjuku_starter_native_batch.py` はこの4画像で認識・移動計画・Aとの分離・
暗転行での単発移動への復帰を検証する。CI上でROMを起動したり、画像間の実入力受付を
再実行したりはしない。6回の入力受付は上記のローカル実測である。

### 残件の再確認

ローカルにある別の保存状態も確認したが、第9話でキャンプ中の3人にSELECTで飛んで
開けたものはいずれも通常のテントで、砦ではなかった。砦の過去の実画像（g1097）はあるが、
その開始保存状態は今回検索した既存チェックアウト・Downloadsには見つからなかった。
確認した別のSRAM2本は全バイトが0で、他のセーブ枠2つも空だった。
別の古い第9話状態から卵回復画面へ進む試行は防衛戦に割り込まれ、複数人の回復対象を
用意できなかった。初回に開けた卵回復画面は対象1人で、2行以上の移動を校正できない。
したがって卵回復・砦の複数行入力は引き続き未確認である。
