# 兵士補充の中止・未成立を記録し、月次スキャンで取り消さない

Issue #2366 の後半「補充をキャンセルしている／補充したつもりで実際にはできていない」への対応（v234、`hanjuku-chart-v234-refill-outcome`）。前半の優先順位（20人以下は補充を最優先）は #2368（v232、[仕様](hanjuku-low-army-refill-first.md)）で対応済み。

## 本番で確認した原因（g809、v222/v227、2026-10-16）

終了済みrun `g809-0b75a42c` の証拠export（Issue #1339 経由、Actions run 38985622825、artifact 12082781692）で、ログが残る1章5年3月〜6年2月の12か月を照合した。

| 月 | 所持金 | 実兵数 | 補充 | 終わり方 |
|---|---|---|---|---|
| 5-7 | 96G | 未読 | 予定16人、未実施 | 兵数確認の開始直後に月次スキャンがメインメニューへ移動し、確認が「未確認」で終了。補充も記録なしで終了 |
| 6-2 | 206G | 未読 | 予定50人、未実施 | 同上。復帰後に募集50G（→150G）と築城5G（→145G）を払い、兵士0人のまま月を終了 |
| 5-8 | 65G | 5人 | なし | 主人公の卵修理費50Gと賃金予備を残すと補充資金がない。理由の記録なし |
| 5-10 | 26G | 16人 | なし | 賃金予備30Gに届かない。理由の記録なし |
| 6-1 | 84G | 29人 | なし | 主人公の卵修理費50G・賃金予備30Gの外の4Gを募集予約に回し、補充0。理由の記録なし |

その他の月（5-3・5-4・5-6・5-9・5-11・5-12）は支払いの照合（`soldier_refill_receipt` が `paid`）まで成立していた。5-5は50人で補充不要だった。

6-2の画面（`decision-004.png`：206Gの月初メニュー、`decision-009.png`：メインメニュー、`frame-070/074.png`：150G・145Gの月初メニュー）を目視で確認した。

### 割り込みの経路

1. 新しい月の最初の観測で `month_step` が兵数確認（`army_count_check`、stage `opening`）を始める。
2. 次に手が読める月初メニューで、`house.step` の無料の月次スキャン（`house_scan_started`、将軍一覧・卵の確認）が `month_step` より先に実行され、メインメニューへ移動する。
3. メインメニューの観測で `army_count_pending_step` が「別の入力所有者」と判定し、確認を `unverified`、`soldiers_done=True` にする（記録なし）。
4. 確認に失敗した月は補充予算を作り直さない（既存の安全側の規則）ため、その月の補充は消える。月初には `month_plan` が「兵士をN人補充します」と実況していた。

卵回復の対象がある月（5-8など）は既存の卵優先の順序がスキャンを止めるため、兵数確認が先に終わっていた。今回の12か月で割り込みが起きたのは、名簿の再確認が必要で卵回復の対象がない5-7と6-2だった。合成画面による再現テストは、#2368 統合後のmain（v232）でも同じ経路で失敗した。

## 変更

- 当月の兵数確認または補充の開始中（`army_count_owned`）、または補充の支払い照合中（`soldier_receipt.status == 'pending'`）は、月次スキャンを開始しない。確認・補充側の待機と試行はいずれも有限なので、スキャンは遅れるだけで止まらない。名簿が未確認の月は、月初の計画どおり兵士の後に募集を判断する（`recruit_before_soldiers: false`）。
- 補充が支払われずに終わった月は、`soldier_refill_outcome` を月1回だけ記録する（`resulting_event` が終わり方）。
  - `cancelled`：確認・補充の途中で戦闘・イベントなど別の画面に移った。
  - `unverified`：兵数を読めない、または確定入力後に支払いを照合できない。購入人数を兵数へ加算しない。
  - `attempt_limit`：会話・数量画面が有限回の待機で開かない、月終了を断る上限に達した。
  - `insufficient_funds`：兵士が50人未満だが、賃金予備と家の卵修理費を残すと補充に回せる資金がない。
  - `not_attempted`：賃金予備と修理費の外に資金があったが、他の予約や優先順位で補充しなかった。予約内訳（卵・募集・修理・賃金予備）を記録する。
- `month_done` の `observed_metric.soldiers` に当月の結果（`paid` と人数、`not_needed`、上の各結果）と実兵数をまとめる。購入の成立は `soldier_refill_receipt` の `paid` だけで、A入力・計画人数・`soldiers_done` は成立とみなさない。
- 実況：`month_plan` の文を「兵士をN人補充する予定です。」に改め、月初に予定を告げた補充が終わらなかった場合だけ、`cancelled` は「今月は中止しました」、`attempt_limit` は「今月は打ち切りました」、`unverified` は「補充できたとは扱いません」と伝える（支払いの有無が不明な場合に「行っていない」とも断定しない）。支払い・人数増加を実況で主張しない。
- 証拠用の判断画像に `soldier_refill_outcome` を加える。
- 50人以上での補充見送り、卵回復見送り後の補充（#2288）、20人以下の補充最優先（#2368）、月初メニューの有界な退出の規則は変更しない。

## 反映と受け入れ

PRのテスト・CI成功、mainへの統合、VM operationsによる正規配布、実プレイでの受け入れは別々に確認する。実プレイでは、名簿未確認かつ卵回復の対象がない月に、同じrunの判断ログで `army_count_check` → `soldiers_seen` → 補充（`soldier_refill_receipt: paid`）または `soldier_refill_outcome` → `house_scan_started` の順になり、`month_done.observed_metric.soldiers` が補充の実結果と一致することを確認する。
