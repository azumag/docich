RGB digest は 256×224 へ正規化したRGB画素のSHA-256で、PNGバイトのSHAではない。
同一 digest は「同じ画像が再観測された」ことだけを示し、入力の受理・拒否を示さない。

`battle_card_missing` / `battle_card_selected`（選択予定）/ `battle_card_candidate`（告知未校正）は

## このPRで校正したこと（v238）

1. `_battle_menu_move`（手順層）: コマンド箱の移動を、実フレームdigest付きで有界化する。
   同一画面が戻っている間は同じ方向入力を繰り返さず待機し、有限回の再試行後は
   Aを送らずBで閉じる（`battle_menu_nav_retry` / `battle_menu_nav_unaccepted`）。
   これが防ぐのは「効かない移動の反復」と「未確認行のA確定」である。digestを持たない
   手組みScreenは従来cadenceのまま。
2. `battle_draw_hold`（orchestrator）: 戦闘が進行中で、直前の観測が戦闘前面
   （battle / battle_menu / battle_menu_pending / okunote_menu / egg_battle_menu /
   egg_choice_menu / monster_menu）であり、現観測が unknown で、既定入力が確定Aのときだけ、
   短い待機に置き換える。上限は `BATTLE_DRAW_HOLD_MAX=3`。箱が描き終われば battle_menu として
   本来の所有者が引き取り、読めないままなら通常の既定入力へ戻る。既に「入力なし」を
   計画している既定（例: HPが隠れたパネルの空入力）は変更しない。

どちらもゲーム・配信・音声・ユーザー休止を操作しない。

## post-mergeレビューで見つかったP2（v238のまま修正）

初回マージ（`830fb38e`）の独立レビューで、`_battle_menu_move` の不受理クローズが
`[pad('b')]`（1要素リスト）を返し、呼び出し側が `[move] if move else []` で包むため
`[[pad('b')]]` になる欠陥が再現された。production のdriverは各要素が object であることを
要求するため（`hanjuku.actions.parse_actions` → `各アクションは object である必要があります`）、
**この脱出経路は実際にはメニューを閉じられなかった**（＝設計した逃げ道が無効だった）。

修正はヘルパーの戻り値を `_battle_menu_to` と同じ契約（単一pad dict / `'here'` / `None` /
保留の `[]`）に揃え、不受理クローズも単一pad dictで返す。あわせて卵戦・切替札の2経路で
「B close」を移動進行として扱わないようにした（切替札では `_card_use_unclassified` により
携行札を差し引かず解放。実使用・消費は確定しない）。

回帰は `tests/test_hanjuku_battle_menu_close_shape.py` がヘルパー契約 → 各コマンド所有者 →
botのstdout JSON → `CommandBrain` まで通しで固定し、修正前の入れ子形が実際に拒否されることも
確認する。既存の `test_hanjuku_battle_menu_nav_stall.py` は入れ子形を期待していたため、
修正後の契約へ更新した（この点はP2の再現そのものを固定していた）。
