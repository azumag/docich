# News PAPER runbook: 隔離・利用条件・Phase別導入/rollback・承認記録（N09）

親Issue #769 / 委任単位 #786（N09）。関連: N00 #775、N01 #776、N02 #778、N03 #779、N04 #780、
N05 #782、N06 #783、N07 #784、N08 #785。

**本書の位置づけ**: 文書化のみ。実装・配備・worker操作・実収集・課金・資格情報の発行は行わない。
本書は「運用を始めてよい」という判断を与えない。各Phaseの開始は、本書の承認票に個別の明示承認が
記録されるまで **未承認** として扱う。CIがgreenであること、Issueがcloseされたこと、実装がmainに
あることは、いずれもPhase開始の根拠にならない。

**mode / 安全境界（全Phaseで固定）**: `mode=paper`、`live_eligible=false`。実注文・broker
credential・live経路は持たない。安全境界を緩めることは本runbookの対象外。

## 0. 用語と記録の区別

- **コード存在**: mainに実装がある（`src/docich/trading/news_paper/`）。運用中であることを意味しない。
- **CI green**: offline試験の合格。実機・実通信の合格を意味しない。
- **Phase開始証拠**: 承認票に個別承認、責任者、対象version/run/scenarioが記録された状態。
- **実機確認**: 許可された専用環境での隔離・通信・時計の実測。未実施なら「未検証」と書く。

報告は「コード存在」「CI」「承認」「実機確認」「評価完了」を別々に書く。片方から他方を推定しない。

## 3. 隔離審査項目（N01/N02/N03/N04）

collector・分類gateway・PAPER管理それぞれについて、以下を審査して記録する。

- **network**: 許可する宛先、プロトコル、DNS の扱い。`network=none` の設定や禁止文字の grep
  だけでは「秘密に到達できない」の証明にしない。
- **UID / mount / path**: 実行UID、読めるmount、書けるpath。state dir 以外への書込がないこと。
- **credential**: 注入方法と、読めるファイル・環境変数の範囲。秘密値は審査記録に採取・貼付しない。
- **cgroup**: CPU/メモリ/プロセス数の有限上限。
- **出力上限**: 1周期あたりの出力サイズ、ログ量、receipt件数。
- **SSRF・リダイレクト**: 取得先の検証、内部アドレスへの到達不可。

実機検証の扱い:

- OS 隔離・実通信の試験は、許可された専用環境でのみ行う（本Issueでは実施しない）。
- 実機未検証なら、そのゲートは **未達** と記録する。offline の単体試験で代替しない。
- 試験で秘密値を採取しない。

## 4. 運用数値の承認票（推奨値と確定値を分離）

以下の数値は、設計レビューで推奨値を出し、承認票へ転記して確定させる。**確定値が承認票に
無い項目は、どのPhaseでも使わない**（実装の既定値も根拠にしない。worker は未指定を起動拒否する）。

| 区分 | 項目 | 推奨値（設計側で記載） | 確定値（承認票） |
|---|---|---|---|
| 対象 | 対象市場・asset数 | 未定 | N00〜N08承認待ち |
| 資金 | 仮想資金、gross/net/通貨exposure上限 | 未定 | N00〜N08承認待ち |
| 損失 | loss上限、drawdown上限 | 未定 | N00〜N08承認待ち |
| 約定 | lot/最小数量、fee、slippage、financing | 未定 | N00〜N08承認待ち |
| 時計 | latency上限、clock_quality判定 | 未定 | N00〜N08承認待ち |
| 周期 | cycle、quote TTL、queue_size、期限 | 未定 | N00〜N08承認待ち |
| 期間 | 評価期間、event数、coverage下限 | 未定 | N00〜N08承認待ち |
| 表示 | dashboard表示範囲 | loopback・allowlistのみ | N09承認待ち |
| 容量 | disk/DB容量上限 | 未定 | N00〜N08承認待ち |
| 上限 | API/token/金額上限 | 未定 | N00〜N08承認待ち |

- 運用閾値（heartbeat・market・news・classifier の age 閾値）も、この表の確定値として承認する。
  閾値が無い間は、age `null` を fresh として扱わない（worker 仕様どおり）。
- 数値が変わる場合（policy/model/source/cost）は新しい run とし、追加承認を取る。

## 5. Phase別ゲート票（Phase 0〜3）

各Phaseは「開始条件・終了条件・停止条件・rollback・責任者」を承認票に固定する。
前Phaseの終了や CI green で次Phaseへ自動的に移らない。

| Phase | 開始条件 | 終了条件 | 停止・rollback |
|---|---|---|---|
| 0 read-only収集 | N00 承認、N01/N02 の offline 契約合格、該当 collector の隔離・権利・quota・保持の審査、Phase 0 の個別承認 | 公表/取得/available の対応精度、欠落・遅延・訂正・重複の標本と人手確認 | source/時計/秘密/SSRF/費用/容量の異常で collector を停止。注文・予約は作らない |
| 1 replay/shadow | Phase 0 の PIT 資料、N03/N04、固定 policy/モデル/費用/評価方法、個別承認 | 未来参照 0、同入力での再現、分類誤り/unknown/遅延の説明、独立レビュー | 漏洩・model drift・不適格資料で shadow を停止。would_accept を実受理へ変換しない |
| 2 PAPER仮想約定 | Phase 1 合格、N05/N06/N07、価格/数量/費用/時計、独立口座・risk・停止試験、個別承認 | 事前に定めた期間/event/coverage と台帳全量の照合 | 二重fill・会計/risk越境・共有DB書込・根拠欠落で新規停止。保有と監査は保全 |
| 3 比較評価 | 固定期間の終了、N08、欠測/未決済/費用が説明可能 | 第三者による再現、指標と限界、次の判断の固定 | 漏洩・事後変更・標本不足は結論保留または無効化。旧 run を消さない |

- Phase 0 の開始に Phase 2 の約定コード完成を要求しない（不要な循環依存を作らない）。
- ただし各Phaseに必要な隔離・診断・承認は、その開始前に必須。
- 全Phase審査の最終完了は、N01〜N08 の必要証拠が揃った後。
- Issue本文の「Phase gates 0-9」の9段階は、現時点で本表（0〜3）以外に定義がない。
  追加のPhaseを使う場合は、承認票で追加定義してから使う。

### 5.1 承認票（Phaseごとに1枚）

```
Phase:            (0 / 1 / 2 / 3)
対象 version:     (コードSHA、設定ファイルのハッシュ)
対象 run / scenario / account: (ID)
許可する外部通信: (宛先・頻度・上限。なしなら「なし」)
許可する予算:     (承認票 §4 の確定値を参照)
許可する操作:     (収集のみ / shadow のみ / PAPER 約定 のいずれか)
開始条件の証拠:   (前Phaseの終了記録へのリンク、実機確認の有無)
終了条件:         (本表の該当行を転記)
停止条件・rollback: (本表の該当行を転記)
責任者:           (氏名/担当。未決なら「未決」と書き開始しない)
個別承認:         (承認者、日時、承認の文言への参照)
未決済の管理先:   (保有・予約・pending の引継ぎ先)
```

承認票が無い、または「未決」の欄が残る場合、そのPhaseは開始しない。

## 6. 障害時の手順

### 6.1 最初の対応（entries_disabled）

1. status（read-only）で、固定 error code・観測時刻・最新の durable receipt/quote sequence・
   保有/pending 件数・監視状態を **保存する**（画面の写しではなく、取得時刻付きで残す）。
2. 新規ニュース判断と risk 増加の pending 買を停止する（worker の `entries_disabled` 仕様）。
3. 継続するもの: 保有評価（valuation）、protective exit（売り）、会計、heartbeat。
4. 固定 error code の意味は [news-paper-worker.md](news-paper-worker.md) §9 を正本とする。

### 6.2 DB不整合・disk full

- 取消や状態更新を無理に書き込まない。新規停止を優先し、監査を保全する。
- 未決済（保有・pending・予約）を明示して記録する。
- **DB backup へ巻き戻して fill を消さない**。巻き戻しは、約定履歴を失わせるため禁止する。
- 古い quote で追いつき、fill を作らない。

### 6.3 全worker停止が必要な場合

- 監視の停止、最終評価時刻、未決済の一覧、引継ぎ責任者を記録してから停止する。
- 引継ぎ先が決まらない停止は、承認票の「未決済の管理先」が「未決」のまま行わない。
- 停止の実行そのものは、正規経路（§1）の個別承認に従う。本書には停止コマンドを置かない。

## 7. 再開手順

再開は、次の全項目を再検証し、記録が揃ってからのみ行う。

- source（利用条件・時刻精度・契約）の変更がないこと。
- clock（clock_quality が trusted）、schema（SCHEMA_VERSION が対応範囲内）。
- 予算と予約残高（上限内、未決済の説明可能）。
- evidence（停止時の証拠が保全され、参照できる）。
- 承認済みの手順と、新しい適格な観測のみで再開する。古い観測の再利用は禁止。

policy/model/source/cost が変わった場合は、新しい run として扱い、追加承認を取る。
旧 run は証拠として保全し、削除・上書きしない。

## 8. 既存経路を巻き込まない

- 既存の worker・配信（音声/映像）・口座・live 経路・price provider は本ユニットの対象外。
- 本ユニットの停止・再開で、既存経路の設定・unit・配信を変更しない。
- 既存の free_strategy・crypto PAPER の資産と合算しない（worker 仕様どおり）。

## 9. 配備時の扱い（将来の別作業）

- 配備・起動は、将来明示承認された場合のみ、現行 AGENTS.md の owner-only 正規経路で
  **別作業として** 扱う。
- systemd unit（`scripts/systemd/docich-news-paper-worker.service`）は静的定義のみ。
  install/enable/restart は本書の対象外で、別承認。
- 本書は VM 操作・再起動の即実行コマンドや権限を含まない。
- VM 配備時の health/queue/diagnostics 統合は未実施。統合されるまで runtime ready と呼ばない。

## 10. 承認と作業の追跡

### 10.1 作業の段階（別々に報告する）

1. 実装完了（コード存在）
2. PR / CI（offline 試験）
3. 配備
4. worker 起動
5. Phase 開始（承認票あり）
6. 実機確認（隔離・通信・時計の実測）
7. 評価完了

各段階の証拠を個別に記録する。前の段階から後の段階を推定しない。

### 10.2 owner作業（資格情報・課金・不可逆操作・外部送信のみ）

owner本人にしかできない作業は、次の形式で1行ずつ書く。

- `owner作業: <内容>`

対象は、資格情報の提供・発行、課金、不可逆操作、外部への送信（GitHub Support 等）、
ログインが要る実機確認に限る。方針判断や推奨で決められる技術判断は owner 作業に含めない。
