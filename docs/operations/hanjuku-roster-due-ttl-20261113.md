# 半熟英雄: 野営帰還の読取要求にTTLを付け、1回の要求で1回だけ読む（v773、2026-11-13）

## 症状（実測 g1163 2026-11-13 16:5x）

`roster_read_due` に、現在の章ではない古い城のエントリが残っていました。

```
roster_read_due = {"えど": 24041, "しらかわ": 23010, "オシロガ": 110273}
tick = 138149
```

`corridor._due_probe` は v772 で `roster_read_due` の城を読むようにしましたが、
この要求は**月の巡回予算とは別（unbudgeted）**で、しかも
`_observe_garrison` が要求を消すのは**完全な名簿を読めたときだけ**でした。
一覧が1ページ（4行）で返る城では要求が消えず、毎プランの先頭に
プローブが割り込み続ける可能性がありました。`オシロガ` の要求は
tick 110273 のまま残っており、約28,000 tick 前の要求です。

## 修正（v773 `hanjuku-chart-v773-roster-due-ttl`）

- `roster_read_due` のエントリは `ROSTER_READ_DUE_TTL=900` tick 以内だけ有効。
  古い要求は無視する。
- 有効な要求は、それが発行したプローブ1回で消費（pop）する。
  一覧が完全でなくても、要求が何度もプローブを生み続けない。
- 野営帰還が再度要求すれば、新しい tick で再登録される。

## 検証

- 新規テスト2件（`tests/test_hanjuku_corridor_probe_budget.py`）
  - 古い `roster_read_due` は無視され、`roster_probe_due` が出ない
  - 新しい要求はプローブ1回で消費される（`roster_read_due` から消える）
- 第9話 corridor / probe / 前線 / capture guard / recall 関連
  **164件 passed**。
- 修正前の `corridor.py` では新テスト2件が失敗することを確認。

## 本番反映後に実測すること

- 古い `roster_read_due` がプローブを生み続けないこと。
- 野営帰還の要求ごとに `roster_probe_due` が1回だけ出ること。
- 帰還先の一覧が読まれ、`garrison` が更新されること（v772 の効果を維持）。

## 残件

- 帰還先の一覧が1ページで complete にならない城では、1回の要求で1回しか
  読まない。帰還将軍が次ページにいる場合は次の帰還要求で再読する。
- 第9話の進行と12話ボス撃破は引き続き実測で確認する。
